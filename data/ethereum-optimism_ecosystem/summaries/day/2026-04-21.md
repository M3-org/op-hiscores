## ACTIVE ISSUES

### Flaky Test Investigations
*   **`TestUnsafeGapFillAfterUnsafeReorg_RestartL2CL` ([#19936](https://github.com/ethereum-optimism/ecosystem/issues/19936))**: This test continues to exhibit flakiness across different CI jobs and branches. The latest comment confirms an occurrence on `memory-all-opn-op-geth` and notes that the underlying race condition is not specific to `op-reth`, despite the existing `FlakyOnOpReth` marker. An investigation into a fix has been launched.
*   **`TestReorgUnsafeHead` ([#20198](https://github.com/ethereum-optimism/ecosystem/issues/20198))**: A new flaky test has been identified. A proposed fix in a draft PR aims to address the root cause, which is attributed to asynchronous updates of `op-node`'s `StatusTracker.data.UnsafeL2` and `Sequencer.latestHead` compared to synchronous EL updates. The fix involves replacing `time.Sleep` with a poll on `SyncStatus().UnsafeL2.Hash` to ensure the sequencer starts with an authoritative unsafe head.

### Kona Interop Block Access Review
*   **`kona-interop: Review access of blocks created internally` ([#19266](https://github.com/ethereum-optimism/ecosystem/issues/19266))**: Discussion continues regarding how `kona-proofs` handles internally created blocks during interop validation. A key point raised is that when a block replacement occurs, the generated receipts are not stored, only the deposit-only block header. This could lead to consolidation failures if other messages reference the deposit-only block and its receipts are needed. The latest comment questions whether deposit-only block receipts should be available from the canonical chain, implying a potential issue if `kona` generates a replacement block that differs from the canonical chain.
