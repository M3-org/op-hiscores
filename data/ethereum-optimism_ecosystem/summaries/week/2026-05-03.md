# ethereum-optimism/ecosystem Weekly Report (May 3 - 9, 2026)

## 🚀 Highlights
This week focused on hardening the infrastructure for interoperability (interop) and streamlining the protocol by removing legacy components. Significant progress was made in validating the interop expiry window through stress testing, which confirmed linear scaling for up to 4096 executing messages and supported extending the window to 7 days. Development velocity saw a boost with the decoupling of Kona prestate builds from Docker, while the CI/CD pipeline was modernized through standardized image build workflows.

## 🛠️ Key Developments

### Infrastructure & CI/CD Enhancements
Efforts this week prioritized developer experience and pipeline consistency.
*   **Standardized Image Builds:** The `build-images.yaml` workflow was migrated to a unified factory plan action, ensuring consistent containerization across the ecosystem ([#1006](https://github.com/ethereum-optimism/ecosystem/pull/1006)).
*   **Kona Development Velocity:** The Kona prestate build process was optimized to run outside of Docker, significantly reducing local build times for developers ([#19057](https://github.com/ethereum-optimism/ecosystem/issues/19057)).

### Protocol Refactoring & Stability
The team worked on simplifying the protocol and resolving synchronization bottlenecks.
*   **Protocol Simplification:** The `ProtocolVersions` contract and its associated deployment paths were removed to eliminate unneeded complexity ([#20309](https://github.com/ethereum-optimism/ecosystem/issues/20309)).
*   **Node Sync Stability:** Critical fixes were implemented for `op-node` to prevent it from getting stuck in Execution Layer (EL) sync mode after restarts when driving `op-reth` ([#18468](https://github.com/ethereum-optimism/ecosystem/issues/18468)).

## 🐛 Issues & Triage

### Closed Issues
*   **Interop & Supernode Functionality:** Resolved issues ensuring new chains can be created post-interop via a new OPCM that deploys chains into independent dependency sets ([#15884](https://github.com/ethereum-optimism/ecosystem/issues/15884)). Additionally, "after head" tests were successfully migrated to `op-supernode` and `op-acceptance-test`, leading to the identification and resolution of a bug in the supernode implementation ([#20370](https://github.com/ethereum-optimism/ecosystem/issues/20370)).
*   **Testing & Validation:** Closed discussions on fetching super roots for unsafe data, opting instead for independent construction of roots in tests to ensure validation integrity ([#19059](https://github.com/ethereum-optimism/ecosystem/issues/19059)).

### New & Active Issues
*   **Superroot Support for Legacy Chains:** A new priority has emerged to support `superroot_atTimestamp` in `op-node` for non-interop chains. This is a prerequisite for fault dispute games following the super-roots upgrade ([#20552](https://github.com/ethereum-optimism/ecosystem/issues/20552)).
*   **Challenger Configuration:** Discussions are underway regarding the consolidation of per-VM flags in `op-challenger`. While global flags would simplify configuration, maintainers noted that distinct flags are currently necessary due to incompatible configuration formats between `op-program` and `kona` ([#20547](https://github.com/ethereum-optimism/ecosystem/issues/20547)).
*   **Stress Testing Results:** Analysis of the interop expiry window ([#15285](https://github.com/ethereum-optimism/ecosystem/issues/15285)) concluded that a 7-day window is viable. A Kona EIP-2935 proof decoding fix was identified during this testing and is pending a merged RLP decoding fix.

## 💬 Community & Collaboration
The week was characterized by high-intensity technical validation and cross-component coordination. Collaboration was particularly evident in the migration of tests to the `supernode` and `op-acceptance-test` suites, involving multiple contributors to ensure coverage for interop scenarios. Technical discussions between maintainers like `sebastianst` and `ajsutton` highlighted a focus on API compatibility and long-term maintainability, specifically regarding how `op-node` should handle super roots before and after the interop activation. There is also a clear trend toward deferring non-blocking documentation (such as the OPCMv2 runbook) to prioritize the shipping of core interop features.
