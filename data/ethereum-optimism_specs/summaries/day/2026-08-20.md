# ethereum-optimism/specs Daily Update (Aug 20, 2026)
## OVERVIEW 
Today's focus was on refining the Kona engine, particularly around safe head management and metric labeling, alongside significant progress on the Lokahi interop actor, including store implementation and verification loop development.

## KEY TECHNICAL DEVELOPMENTS

### Kona Engine Refinements and Metric Enhancements
Discussions and implementations continued for the Kona engine, focusing on explicit local-safe/cross-safe vocabulary and a single promotion entry point for cross-safe. This ensures consistent handling of safe heads and prevents issues during rewinds. Additionally, efforts were made to add `chain_id` labels to Kona's metrics, improving observability and debugging for multi-chain environments.
- [#22525](https://github.com/ethereum-optimism/specs/issues/22525)
- [#22529](https://github.com/ethereum-optimism/specs/issues/22529)
- [#22526](https://github.com/ethereum-optimism/specs/issues/22526)

### Lokahi Interop Actor and Store Development
Significant progress was made on the Lokahi interop actor, including the development of its persistent stores (verifiedDB, logsDBs, and invalidated-output archive). This foundational work is crucial for the interop actor's state management and replay capabilities. Discussions also covered the retention policy for superroots and the design of the `Contains` operation for the logsDB.
- [#22535](https://github.com/ethereum-optimism/specs/issues/22535)
- [#22522](https://github.com/ethereum-optimism/specs/issues/22522)

### Multi-Chain L1 Watcher and Service Composition
Work advanced on generalizing the L1 watcher to handle multiple chains, enabling a single watcher to fan out L1 messages to various derivation actors. This is a key step towards multi-chain service composition within Lokahi, allowing for the orchestration of N chains within a single process.
- [#22531](https://github.com/ethereum-optimism/specs/issues/22531)
- [#22532](https://github.com/ethereum-optimism/specs/issues/22532)

### Interop Message Validity Rules Consolidation
Efforts continued to consolidate shared interop message validity rules into a single location within `kona-interop`. This ensures that both the Lokahi verifier and the proof side apply identical rules, preventing divergence. Discussions clarified the scope of checksum computation and the API shape for these rules.
- [#22534](https://github.com/ethereum-optimism/specs/issues/22534)

## CLOSED ISSUES
- **Removal of Cross-Unsafe Chain-Head Notion**: Issue [#22550](https://github.com/ethereum-optimism/specs/issues/22550) was closed, addressing the removal of the cross-unsafe chain-head concept from Go-side components (op-node, op-service, op-devstack). This was identified as an op-supervisor-era vestige that no longer serves a purpose in the current interop design, as it merely shadowed the unsafe head. The message-level cross-unsafe validation threshold in the tx-pool admission path remains untouched due to its active functionality.

## ACTIVE ISSUES

### Kona Engine: Targeted Reset and Safe Head Management
Issue [#22526](https://github.com/ethereum-optimism/specs/issues/22526) discusses the implementation of a targeted reset (`reset_to` with explicit heads) for the Kona engine. The latest comment from claude confirms the implementation in #22586 and provides detailed notes on how resets interact with the cross-safe head. It clarifies that "Resets never move cross-safe" means never moving it *forward*, and that rewinds require explicit handling to prevent stale `safeBlockHash` values. The comment also highlights a structural difference between `op-node` and `kona` in managing the cross-safe head, with `op-node` recomputing it on every read while `kona` stores it. The discussion emphasizes that the cross-safe bound belongs in the state transition rather than the reset itself, and notes a deliberate difference in retry behavior between `reset` and `reset_to`.

### Kona Engine: Local/Cross-Safe Vocabulary and Promotion Entry Point
Issue [#22525](https://github.com/ethereum-optimism/specs/issues/22525) focuses on renaming head vocabulary to explicit local-safe/cross-safe and establishing a single promotion entry point for cross-safe. claude's latest comment details the implementation in #22576, stacked on #22519. Key takeaways include the enforcement of the "exactly one promoter per engine" property at the crate boundary, the re-pointing of certain heads (e.g., derivation actor uses local-safe, `FinalizeTask` uses cross-safe), and a discrepancy between `cargo test` and `cargo nextest` for this crate due to global recorder installation. The comment also mentions a rebase vs. merge decision during a force-push and the verification steps taken.

### Kona: Chain_ID Metric Labeling
Issue [#22529](https://github.com/ethereum-optimism/specs/issues/22529) addresses adding a `chain_id` label dimension to Kona's existing metric names. claude's latest comment outlines the implementation in #22569. It notes that the existing macro surface for metrics could not express variadic labels, leading to a change in the order of arguments for `set!` and `record!` macros. The comment also points out that the `test_chain_label_metrics` unit test was not passing due to global recorder installation and was updated to use `metrics::with_local_recorder`. The scope of the implementation was limited to `kona-engine` (14 call sites), with a design decision to put `chain_id: u64` on `EngineState` for easier threading. Several pre-existing lint snags and unaddressed issues (e.g., `SharedString` allocation for chain IDs, `Metrics::zero` vs. runtime `inc!` schema disagreement) are also highlighted.

### Lokahi: Interop Actor, Cross-Safe Happy Path (Phase 3)
Issue [#22522](https://github.com/ethereum-optimism/specs/issues/22522) tracks the development of the Lokahi interop actor's cross-safe happy path. claude's latest comment provides an index of phase-3 decisions from a Slack design discussion, linking them to specific issues. These decisions cover retention and storage engine, WAL-replay hazard for the invalidated-output archive, and a divergence in activation sources between Kona and op-supernode that requires a human decision.

### Lokahi: N-Chain Service Composition and Config
Issue [#22532](https://github.com/ethereum-optimism/specs/issues/22532) concerns growing `rust/lokahi` for N-chain service composition and configuration. claude's latest comment confirms the landing of #22599, which enables running N chains in one process with layered configuration, per-chain data directories, RPC sockets, and metric registration. It details how the L1 head watch, watcher attachment, and engine's chain ID were handled during the merge of parallel branches. The comment also notes a latent test bug exposed by the merge and a hand-off for #22533 regarding CI job persistence for `lokahi` binaries. An earlier comment from claude, based on a decision from @ajsutton, clarifies that the L1 watcher's fixed, non-empty chain set is correct by design, as chains cannot be dynamically added to a running instance, and a zero-chain configuration is invalid.

### Kona-Interop: Consolidate Shared Message-Validity Rules
Issue [#22534](https://github.com/ethereum-optimism/specs/issues/22534) aims to consolidate interop message-validity rules into `kona-interop`. The latest comment from @sebastianst, generated by Claude, highlights that the type-3 access-list checksum computation currently lacks a Rust counterpart in `kona-interop`. It suggests that this computation, crucial for Lokahi's verifier, should be included in the shared rules with a Go↔Rust golden vector. An earlier comment from claude, based on @ajsutton's ruling, clarifies that checksum existence is an implementation detail of the log store for space efficiency, not a consensus-protocol check, and thus belongs in Lokahi's logsDB layer rather than shared validity rules. Another comment from claude details the decision to make the shared interop rules surface a type (`MessageRules`) rather than free functions, improving code organization and discoverability. The comment also provides an enumeration of pre-existing implementations of the five rules, noting Rust↔Go divergences in activation source, expiry arithmetic, and initiating-message existence.
