# ethereum-optimism/specs Daily Update (Apr 21, 2026)
## OVERVIEW 
The day saw significant progress in interop fault proofs and infrastructure, with several long-standing issues related to message expiry consolidation and contract deployments being resolved. Discussions also continued on flaky tests and the future of op-geth.

## KEY TECHNICAL DEVELOPMENTS

- None

## NEWLY OPENED PULL REQUESTS
- None

## CLOSED ISSUES

- **Interop Fault Proofs and Message Expiry Consolidation:** The issue of output root mismatch after deposit-only block replacement during message expiry consolidation in Kona was resolved. This involved several prerequisite merges, including configurable message-expiry windows, challenger passing `--depset-cfg` to kona-host, fixing re-execution hangs, and removing an obsolete replacement deposit transaction that caused the output root mismatch. The relevant tests now pass across both op-geth and op-reth fault-proofs jobs. ([#19848](https://github.com/ethereum-optimism/specs/issues/19848))
- **Contract Feature Flags and Deployments:** Several issues related to the deployment and integration of the OPSuccinct feature flag within Optimism contracts were closed. This included creating the feature flag, adding it to the OPCM `_devFeatureBitmap`, and integrating it into `DeployImplementations.s.sol`. ([#18419](https://github.com/ethereum-optimism/specs/issues/18419), [#18420](https://github.com/ethereum-optimism/specs/issues/18420))
- **Kona Interop and CrossL2Inbox Deployment:** The issue of Kona unconditionally generating CrossL2Inbox transactions was addressed. A fix was implemented to conditionally deploy the CrossL2Inbox based on the number of chains in the dependency set, aligning Kona's behavior with Go's `InteropNetworkUpgradeTransactions()`. ([#19311](https://github.com/ethereum-optimism/specs/issues/19311))
- **Documentation and Unused Dependencies:** An issue concerning an unused `toml` npm dependency in the documentation was closed, indicating a cleanup of the `docs/public-docs/package.json` file. ([#20017](https://github.com/ethereum-optimism/specs/issues/20017))
- **Interop Application Behaviors:** A very old issue related to interop application behaviors, including checking chain readiness and recording results and metadata, was closed as the work has long been completed. ([#18742](https://github.com/ethereum-optimism/specs/issues/18742))
- **Op-geth Deprecation Clarification:** An inquiry regarding the mandatory use of op-reth and the continued use of op-geth was closed with a clarification that op-geth can be used through May 31st, with further details available in the official deprecation plan. ([#20203](https://github.com/ethereum-optimism/specs/issues/20203))

## NEW ISSUES

- **Interop Specification Updates:** A new issue was opened to update the interop specifications to reflect the latest semantics, specifically the removal of same-timestamp and the simplification of replacement blocks. ([#905](https://github.com/ethereum-optimism/specs/issues/905))

## ACTIVE ISSUES

- **Flaky Test: `TestUnsafeGapFillAfterUnsafeReorg_RestartL2CL` ([#19936](https://github.com/ethereum-optimism/specs/issues/19936))**: This test continues to exhibit flakiness, now observed on `memory-all-opn-op-geth` in addition to op-reth. The underlying race condition is not reth-specific. An investigation into a fix has been launched.
- **Kona-Interop: Review access of blocks created internally ([#19266](https://github.com/ethereum-optimism/specs/issues/19266))**: Discussion revolves around how Kona-proofs handles receipts for internally generated replacement blocks. While the specific concern about re-querying replaced non-canonical blocks was addressed, a new issue was identified: receipts for deposit-only replacement blocks are not stored, which could lead to consolidation failures if other messages reference these blocks.
- **Flaky Test: `TestReorgUnsafeHead` ([#20198](https://github.com/ethereum-optimism/specs/issues/20198))**: A proposed fix in ethereum-optimism/optimism#20201 (draft) addresses this flaky test. The root cause was identified as an asynchronous update of op-node's `SyncStatus().UnsafeL2` and `Sequencer.latestHead`, leading to the sequencer building on a stale parent. The fix involves replacing `time.Sleep` with a poll on `SyncStatus().UnsafeL2.Hash` before starting the sequencer.
