# ethereum-optimism/specs Weekly Report (Apr 5 - 11, 2026)

## 🚀 Highlights
This week, development focused on enhancing protocol documentation and addressing stability issues within the testing suite. A significant addition to the specifications was the introduction of a guide for Jovian L1Block Scalar Parsing, supporting the evolution of the OP Stack's data handling. Meanwhile, engineering efforts were heavily directed toward diagnosing race conditions and timing inconsistencies in CI tests, particularly those affecting Flashblocks and L2 consensus layer restarts.

## 🛠️ Protocol Specifications & Documentation
The primary technical advancement this week involved refining how the protocol interacts with L1 data.

### Jovian Upgrade Specifications
- **L1Block Scalar Parsing:** A new guide was introduced to specify the parsing logic for Jovian L1Block scalars ([#901](https://github.com/ethereum-optimism/specs/pull/901)). This work is essential for ensuring that L2 nodes correctly interpret L1 state data following the Jovian upgrade, maintaining consistency across the Superchain.

## 🐛 Issues & Triage
The week's triage activity was dominated by the investigation of flaky tests that impact CI reliability and developer velocity.

### Flaky Test Investigations
Maintainers are currently investigating two primary sources of non-deterministic test failures:
- **Flashblocks Timing Issues:** Analysis of `TestFlashblocksTransfer` ([#19934](https://github.com/ethereum-optimism/specs/issues/19934)) revealed a timing race condition. Logs indicate instances where a transaction's block time exceeded the flashblock's time by two seconds, suggesting a need for tighter synchronization or adjusted assertions in the test environment.
- **L2 Consensus Layer Reorgs:** The `TestUnsafeGapFillAfterUnsafeReorg_RestartL2CL` ([#19936](https://github.com/ethereum-optimism/specs/issues/19936)) has been confirmed as flaky after multiple occurrences. The failure—an "operation failed permanently after 50 attempts"—points to an issue with the head matching the "unsafe" state after a restart, which could signal edge cases in how the node handles unsafe gap fills during reorgs.

## 💬 Community & Collaboration
Collaboration this week was characterized by deep technical debugging between core contributors. Developers **wwared** and **maurelian** actively collaborated on the flaky test investigations, providing critical CI run contexts and log analysis to isolate the root causes of the race conditions. This high level of engagement on infrastructure stability reflects a continued commitment to protocol security and a robust developer experience.
