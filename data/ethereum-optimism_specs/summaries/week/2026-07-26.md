# ethereum-optimism/specs Weekly Report (Jul 26 - 1, 2026)

## 🚀 Highlights
This week focused on advancing the infrastructure for the Superchain through the introduction of Predictive Chain Deployment (PCD) specifications and critical architectural discussions regarding OPCM upgrades. A significant milestone was reached with the formalization of PCD contracts and deployment workflows, aimed at streamlining how new chains join the ecosystem. Meanwhile, the team tackled complex governance and technical debt questions surrounding post-migration upgrades for interoperable chain sets, prioritizing consistency and safety in shared component management.

## 🛠️ Key Developments

### Predictive Chain Deployment (PCD)
The primary technical addition this week was the introduction of comprehensive specifications for Predictive Chain Deployments. This work establishes the framework for how chains are instantiated within the ecosystem, ensuring a standardized approach to contract deployment and tooling.
*   **PCD Specifications:** Added detailed documentation covering the necessary smart contracts, the role of the `OP-deployer`, and a high-level overview of the deployment lifecycle ([#921](https://github.com/ethereum-optimism/specs/pull/921)). This addresses foundational requirements for scaling the Superchain efficiently.

## 🐛 Issues & Triage

### Closed Issues
*   **Proposer Instance Management:** An investigation into the `kona-sp1-proposer` regarding the detection of multiple instances running with the same key was concluded. Maintainers determined that the complexity required to implement a robust detection mechanism outweighed the minor risks associated with the occurrence, leading to the closure of the issue ([#22020](https://github.com/ethereum-optimism/specs/issues/22020)).

### Active Issues & Discussions
*   **Post-Migration OPCM Upgrades:** Significant debate continues regarding how the Optimism Package Manager (OPCM) should handle upgrades for chains within an interoperability set ([#21731](https://github.com/ethereum-optimism/specs/issues/21731)). The core challenge lies in managing shared components when multiple chains share a `ProxyAdmin`. 
    *   The team is currently leaning toward an approach where `OPCM.upgrade` is idempotent, allowing all chains to attempt upgrades on shared components. 
    *   This "Option 1" is favored over skipping updates, as it reduces the risk of partial upgrades or incompatible contract states, though it necessitates rigorous post-upgrade verification.

## 💬 Community & Collaboration
The week's activity highlights a strong focus on consensus-building around protocol upgrades. The technical discussion in [#21731](https://github.com/ethereum-optimism/specs/issues/21731) demonstrates active collaboration between contributors to weigh the trade-offs between implementation complexity and system reliability. The resolution of the `kona-sp1-proposer` issue also reflects a pragmatic approach to project management, where the community prioritizes high-impact features over unnecessary architectural complexity.
