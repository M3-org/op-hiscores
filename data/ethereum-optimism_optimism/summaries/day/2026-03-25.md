# ethereum-optimism/optimism Daily Update (Mar 25, 2026)

## OVERVIEW

Today's development focused on integrating a new ZK dispute game, enhancing devstack flexibility, and refining acceptance tests. Significant progress was made in addressing a critical bug in L1Retrieval and streamlining contract management.

## KEY TECHNICAL DEVELOPMENTS

### ZK Dispute Game Integration and Contract Refinements

A new spec-compliant ZK Dispute Game was integrated into the OP Stack dispute infrastructure, replacing the previous `OptimisticZkGame` and implementing the full game lifecycle [#19606](https://github.com/ethereum-optimism/optimism/pull/19606). Concurrently, several interop bridge contracts were removed from the L2ContractsManager upgrade flow, streamlining contract management and reducing the implementation count [#19650](https://github.com/ethereum-optimism/optimism/pull/19650).

### Devstack Enhancements and Acceptance Test Migrations

The devstack now respects `DEVSTACK_L2EL_KIND` and `DEVSTACK_L2CL_KIND` across all single-chain runtimes, introducing central environment-aware dispatch functions for L2EL and L2CL startup [#19653](https://github.com/ethereum-optimism/optimism/pull/19653). Acceptance tests were also migrated to use supernode-based presets and updated to work against `op-reth`, with specific tests being skipped for `op-reth` where mechanical changes were not feasible [#19754](https://github.com/ethereum-optimism/optimism/pull/19754), [#19676](https://github.com/ethereum-optimism/optimism/pull/19676). A specific action test for `DeepCanonicalBlockQuery` was removed as it no longer aligns with current EIP-2935 block hash verification methods [#19753](https://github.com/ethereum-optimism/optimism/pull/19753).

### Critical Bug Fixes and Infrastructure Improvements

A bug in `L1Retrieval` was addressed, ensuring that the Data Availability Provider (DAP) is cleared on reset or activation signals to prevent stale calldata or blobs from persisting across re-orgs [#19687](https://github.com/ethereum-optimism/optimism/pull/19687). Additionally, the L1 geth in `op-devstack` was configured to expose its user RPC over HTTP to accommodate Kona's connection requirements [#19742](https://github.com/ethereum-optimism/optimism/pull/19742). CI workflows were optimized by skipping rust gate and devnet metrics collection for documentation-only pull requests [#19739](https://github.com/ethereum-optimism/optimism/pull/19739), [#19744](https://github.com/ethereum-optimism/optimism/pull/19744).

## CLOSED ISSUES

### Kona Guest Program Stability

The issue where the Kona guest program panicked due to a missing `name` field when deserializing `chainList.json` has been resolved [#19654](https://github.com/ethereum-optimism/optimism/issues/19654). This fix addresses a critical stability problem during Cannon VM execution.

### Kona Interop Block Hash Oracle Review

The tracking issue for reviewing the `kona-interop` block hash oracle, specifically its use of EIP-2935 for efficient block hash lookups, has been closed [#18288](https://github.com/ethereum-optimism/optimism/issues/18288). Progress included adding a fixture-based integration test for `OracleInteropProvider::header_by_number` in `kona-proof-interop` to validate the EIP-2935 code path without requiring lengthy acceptance tests.

### ZK Dispute Game Contract Updates

Several issues related to the ZK dispute game contracts have been closed, indicating significant progress in their development and integration. This includes removing the access manager [#18418](https://github.com/ethereum-optimism/optimism/issues/18418), replacing `rollupConfigHash` with `l2ChainID` [#18421](https://github.com/ethereum-optimism/optimism/issues/18421), and ensuring MCP compatibility [#18417](https://github.com/ethereum-optimism/optimism/issues/18417).

## NEW ISSUES

### `op-alloy` Compilation Conflict

A new issue has been identified where `op-alloy-network` fails to compile against alloy 1.8 due to a conflicting `NetworkWallet` implementation [#19755](https://github.com/ethereum-optimism/optimism/issues/19755). This conflict arises from a blanket implementation introduced in `alloy-network` version 1.8.

## ACTIVE ISSUES

### Flaky `TestCLELDivergence`

The `TestCLELDivergence` test continues to exhibit flakiness, with recent discussions focusing on the root cause of unexpected resets during the derivation pipeline [#19681](https://github.com/ethereum-optimism/optimism/issues/19681). A potential mitigation has been implemented, and the issue remains open to confirm if the flakiness has been resolved. The core question revolves around whether the observed reset behavior in step 3 of the derivation process is correct or indicative of a deeper bug in the reset logic, as it impacts the test's ability to reliably observe CL-EL divergence.
