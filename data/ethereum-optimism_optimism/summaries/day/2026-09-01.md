# ethereum-optimism/optimism Daily Update (Sep 1, 2026)
## OVERVIEW 
Today's development focused on critical bug fixes in `op-challenger` and CI, alongside significant internal refactoring to streamline `op-service` and `op-batcher` dependencies. Documentation was enhanced with a new RPC provider, and several key issues related to migration paths and lightnode deployments were closed.

## KEY TECHNICAL DEVELOPMENTS

### Interoperability and Proving System Enhancements
A critical bug in `op-challenger` was fixed, addressing an issue where the interop VM runner selected an unusable game L1 head, preventing proper claim serving ([#22727](https://github.com/ethereum-optimism/optimism/pull/22727)). Additionally, improvements were made to the Kona SP1 prover to retain proving progress across retries, preventing loss of completed chunks and SPN request IDs after failures ([#22717](https://github.com/ethereum-optimism/optimism/pull/22717)).

### Infrastructure and Dependency Streamlining
Significant refactoring was undertaken to reduce dependencies and improve modularity. The `PathFlag` was moved to a new leaf package in `op-service` to allow `oppprof` to be imported downstream without pulling in the superchain config bundle ([#22700](https://github.com/ethereum-optimism/optimism/pull/22700)). The `op-batcher`'s dependency on the `superchain-configs.zip` bundle was removed, and `op-node` now builds its display map without parsing every embedded chain config at initialization ([#22712](https://github.com/ethereum-optimism/optimism/pull/22712)).

### CI/CD and Documentation Updates
CI configurations were updated to bump the `circleci-utils` orb to version 1.0.31, which includes a fix for stale PR close timing ([#22723](https://github.com/ethereum-optimism/optimism/pull/22723)). The `apko` factory pin was also updated to restore version stamping in image builds ([#22722](https://github.com/ethereum-optimism/optimism/pull/22722)). Documentation was enhanced by adding SolidRPC to the OP Stack production RPC provider directory, detailing its support for various mainnets and testnets ([#22710](https://github.com/ethereum-optimism/optimism/pull/22710)).

## CLOSED ISSUES

### Migration and Deployment Progress
The issue tracking the implementation and testing of all in-scope migration paths via `OPCMv2.upgrade()` has been closed ([#20757](https://github.com/ethereum-optimism/optimism/issues/20757)). Additionally, the task to re-deploy Lightnode across staging environments to validate light nodes for interop preparation has been completed and closed ([#22352](https://github.com/ethereum-optimism/optimism/issues/22352)).

### Proving System Reliability
A critical issue where game-proving retries discarded completed proofs and regenerated all witnesses has been resolved and closed ([#22622](https://github.com/ethereum-optimism/optimism/issues/22622)). This fix ensures that progress is retained during multi-chunk game proving.

## NEW ISSUES

### Prover Resilience and State Management
A new issue has been opened to track future work on making the `kona-sp1-proposer` durable across restarts, specifically to support restarts without losing in-flight proofs, which currently wastes time and money ([#22726](https://github.com/ethereum-optimism/optimism/issues/22726)).

### Contract Validation Inconsistencies
A problem has been identified in `contracts-bedrock` where `OPContractsManagerMigrationValidator.MIG-SASR-RGT` accepts super game types that the migration validator never validates, potentially leading to inconsistencies ([#22731](https://github.com/ethereum-optimism/optimism/issues/22731)).

## ACTIVE ISSUES

### Kona Node Network Actor Stalling
Discussion continues on [#22646](https://github.com/ethereum-optimism/optimism/issues/22646), which addresses the `NetworkActor` in `kona-node` stalling the p2p swarm during remote-signer HTTP calls. @geoknee provided clarification to @jdodinh regarding design parity with other implementations and the preference for smaller PRs. @jdodinh expressed interest in picking up the issue, proposing to measure the degraded case against a signer with injected latency to confirm the stalling behavior. Key questions raised by @jdodinh include whether to maintain parity with the overflow policy chosen in #22585 (small bound, drops oldest) and if the deadline change could be landed separately from larger restructuring efforts.
