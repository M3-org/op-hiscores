## ACTIVE ISSUES

### op-supernode: Observations from Mirroring in Lokahi ([#22636](https://github.com/ethereum-optimism/optimism/issues/22636))
Discussions on this issue detail discrepancies found between the Dafny model and `op-supernode`'s Go implementation while mirroring its behavior in Lokahi. Key points from the latest comment include:
- **Verification Discrepancies**:
    - Executing messages in the first sealed block are never verified in Go, a potential verification hole.
    - Model requires frontier view for same-timestamp initiating messages, while Go falls through to `logsDB`.
    - Frontier view correctness is an axiom in the model but not checked in Go.
- **Logs Store Issues**:
    - Virtual-parent first-block seal in Go violates the `UpdatedLogsDB` axiom.
- **Rewind Plan Inconsistencies**:
    - `buildRewindPlan` in Go produces plan shapes that the model's `ValidRewindPlan` cannot express.
    - Rewind apply order differs: engines-first in model vs. engines-last in Go.
- **Observation and Decision Differences**:
    - `observeRound`'s two-flag L1 split in Go has no model analog.
    - `obs.L2sConsistent` is never set in Go, making related model gates vacuously discharged.
    - `checkChainsReady`'s at-most-one-block advance is assumed in the model but not checked in Go.
- **Commit and Lifecycle Variations**:
    - VerifiedDB commit is strictly-next in the model vs. idempotent replay in Go.
    - The all-chain VN freeze during invalidation in Go is not modeled.
    - Go's I/O-error paths are outside the model's scope, leading to unspecifiable partial states.

Additional comments highlight:
- **Kona-node RPC Gaps**: `kona-node` lacks the `opstack` block-building namespace and the `superroot` namespace present in `op-node`, causing `Method not found` errors for test sequencers and dispute infrastructure.
- **L1 Reorg Behavior**: A deep post-commit L1 reorg can still wipe history and halt verification permanently, mirroring `op-supernode`'s behavior.
- **CI Job Naming**: A CI job named `memory-all-kona-lokahi-op-reth-<fork>` was found to be running `supernode_kind: op-supernode` instead of `lokahi`, leading to false positives regarding Lokahi's acceptance test pass rates. This issue emphasizes the need for accurate job naming and clear reporting of the measured implementation.
