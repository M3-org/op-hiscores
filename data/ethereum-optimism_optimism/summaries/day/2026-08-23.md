## ACTIVE ISSUES
### op-supernode: observations from mirroring its behaviour in lokahi ([#22636](https://github.com/ethereum-optimism/optimism/issues/22636))
Discussions on this issue revolve around discrepancies found between the Dafny model and `op-supernode`'s Go implementation while mirroring its behavior in `lokahi`. Key points from the latest comments include:
*   **Verification Discrepancies**:
    *   The model ensures every frontier block is cross-valid, while Go silently skips verification for executing messages in the first sealed block, creating a potential verification hole. The model's approach is preferred.
    *   For same-timestamp initiating messages, the model requires the frontier view, while Go falls through to the `logsDB`. Go's approach is deemed more appropriate given varied block times.
    *   The model axiomatically ensures frontier view correctness, but Go's implementation assumes it without checking. Go should add an equality check to discharge this axiom.
*   **Logs Store**: The model's `UpdatedLogsDB` axiom is violated by Go's virtual-parent first-block seal. A decision is needed to either widen the axiom or drop the extra seal.
*   **Rewind Logic**:
    *   `buildRewindPlan` in Go produces plan shapes that the model's `ValidRewindPlan` cannot express, suggesting the model needs generalization.
    *   The rewind apply order differs between the model (engines-first) and Go (engines-last), with implications for partial-failure semantics.
*   **Observation and Decision**:
    *   Go's `observeRound` uses a two-flag L1 split (`L1NeedsRewind`, `L1Consistent`) which has no direct model analog. The two-flag split is preferred for distinguishing "rewind needed" from "wait".
    *   Go never sets `obs.L2sConsistent`, making it dead code, while the model relies on it. Semantics need to be aligned.
    *   Go assumes a single-block advance in `checkChainsReady` without checking, which the model assumes. Either a precondition on `OptimisticAt` or a runtime check is needed.
*   **Commit and Lifecycle**:
    *   The model's `VerifiedDB.Commit` requires the strictly next timestamp, while Go accepts idempotent replay, which is necessary for WAL crash-replay. The model should admit idempotent equal-replay.
    *   The all-chain VN freeze during invalidation in Go is not modeled, but appears load-bearing for race-freedom. The model should incorporate this concept.
    *   Go's I/O-error paths are outside the model's scope, leading to partially-written states that the model's invariants cannot describe. A scope decision is needed to either model failure/atomicity explicitly or document assumptions.
*   **Sibling Gaps**:
    *   `kona-node` lacks the `superroot` namespace present in `op-node`, leading to `Method not found` errors for dispute infrastructure pointing at a standalone `kona-node` RPC.
    *   `kona-node` also lacks `op-node`'s `opstack` block-building namespace (`opstack_openBlockV1`, `sealBlockV1`, etc.), causing `Method not found` errors for the `op-test-sequencer`.
*   **CI Job Naming**: A `memory-all-kona-lokahi-op-reth-<fork>` CI job was found to be running `op-supernode` instead of `lokahi`, leading to false positives. This highlights the need for accurate job naming and verification that the intended binary is actually running.
