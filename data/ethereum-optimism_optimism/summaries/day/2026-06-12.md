# ethereum-optimism/optimism Daily Update (Jun 12, 2026)
## OVERVIEW 
Today's development focused on integrating ZKDisputeGame into OPCMv2, enhancing `op-challenger` with JSON output, and significant documentation updates. Several CI/CD fixes and Rust-related chores were also completed, alongside the closure of multiple issues related to ZK game integration.

## KEY TECHNICAL DEVELOPMENTS

### ZKDisputeGame Integration and OPCM Enhancements
The `ZKDisputeGame` (game type 10) has been integrated into OPCMv2, including super-root semantics, upgrade/deploy plumbing, validator checks, factory wiring, and `op-deployer` support. This is a major step towards supporting ZK proofs within the Optimism ecosystem. ([#21156](https://github.com/ethereum-optimism/optimism/pull/21156))

### Developer Tooling Improvements
The `op-challenger` command-line tool now supports a `--format json` option for `list-claims` and `list-games`, making programmatic consumption and AI agent integration easier. ([#21329](https://github.com/ethereum-optimism/optimism/pull/21329))

### CI/CD and Rust Toolchain Updates
Several fixes were implemented for CircleCI manual dispatch continuation parameters and cache keying for vendored Rust binaries. Unnecessary dependencies were reverted, and `mold` was added to speed up Rust binary linking. ([#21364](https://github.com/ethereum-optimism/optimism/pull/21364), [#21208](https://github.com/ethereum-optimism/optimism/pull/21208), [#21362](https://github.com/ethereum-optimism/optimism/pull/21362))

### Documentation and Codebase Refinements
Documentation for proxyd v4.28.0 release was added, and an AI skill for updating the Reth dependency was introduced, along with folding bump learnings into the guide. Unused `op-supervisor` packages were removed to streamline the codebase. ([#21366](https://github.com/ethereum-optimism/optimism/pull/21366), [#21357](https://github.com/ethereum-optimism/optimism/pull/21357), [#21369](https://github.com/ethereum-optimism/optimism/pull/21369))

## ACTIVE ISSUES

### Centralizing OP Fork to L1 Fork Mapping
Discussion on [#21338](https://github.com/ethereum-optimism/optimism/issues/21338) highlights the problem of duplicated OP fork to implied L1 (Ethereum) fork mapping across seven different sites in the codebase. A detailed plan has been proposed to centralize this mapping in `alloy-op-hardforks` as a single source of truth, with derived views for different consumers. A latent bug was identified where `kona/crates/protocol/genesis/src/rollup.rs` was missing the `Karst → Osaka` mapping. The proposed solution involves creating a canonical table in `alloy-op-hardforks`, rewiring direct consumers, eliminating OP-fork knowledge from `kona-engine` where possible, and adding consistency tests for `op-revm` without introducing new dependencies.

### Proofs: Faster Withdrawals with ZK
On [#20774](https://github.com/ethereum-optimism/optimism/issues/20774), the discussion revolves around increasing `MAX_CLOCK_DURATION` and reducing air gap constants for faster ZK withdrawals. A key point raised is the unbounded nature of max history needed, depending on proposal frequency. It's noted that for 1-day withdrawals, the max history for a proof would be no longer than 1 day, and challenging doesn't require history as the correct output root can be reconstructed from the withdrawal root.
