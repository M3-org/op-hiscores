# ethereum-optimism/optimism Daily Update (Jan 20, 2026)
## OVERVIEW 
Today's development focused on significant CI/CD improvements, including refactoring for continuations and fixing release triggers. Contract tests were updated to run U18, and several bug fixes and dependency upgrades were implemented, alongside new custom linters and challenger game handling improvements.

## KEY TECHNICAL DEVELOPMENTS

### CI/CD Enhancements and Fixes
The CI/CD pipeline saw substantial refactoring to incorporate CircleCI continuations, enabling more efficient workflow execution based on path filtering [#18812](https://github.com/ethereum-optimism/optimism/pull/18812). A critical fix was also implemented to ensure proper continuation of git tag release triggers, addressing issues where dynamic config pipelines might skip continuation [#18880](https://github.com/ethereum-optimism/optimism/pull/18880).

### Contract Test Updates and Dependency Upgrades
Contract tests were updated to run U18, enhancing the testing framework for `contracts-bedrock` [#18768](https://github.com/ethereum-optimism/optimism/pull/18768). Additionally, `op-geth` was upgraded to upstream v1.16.6, ensuring the project benefits from the latest Geth improvements [#18338](https://github.com/ethereum-optimism/optimism/pull/18338).

### Code Quality and Challenger Game Improvements
New custom linters were introduced to prevent common errors, such as incorrect usage of `big.Int Uint64`, improving overall code quality [#18815](https://github.com/ethereum-optimism/optimism/pull/18815). The `op-challenger` also received improvements for handling corner cases in dispute games, enhancing its robustness [#18860](https://github.com/ethereum-optimism/optimism/pull/18860). A minor bug fix corrected a typo in the `op-validator` codebase, clarifying the meaning of CKDG [#18734](https://github.com/ethereum-optimism/optimism/pull/18734).

## ACTIVE ISSUES

### op-supernode: Reset Handling [#18740](https://github.com/ethereum-optimism/optimism/issues/18740)
Discussion continues on how `op-supernode` should handle resets, particularly concerning the `engine_forkchoiceUpdatedV1` behavior. The latest comments explore several options:
- **Option 1 (Hack around FCU):** Update to a synthetic block and then back to the desired block. This is currently the preferred approach for the short term.
- **Option 2 (Supernode-driven resets):** Attempt to make supernode-driven resets mimic regular pre-interop reorgs, though its feasibility is questioned given the new supernode design.
- **Option 3 (New Engine API method):** Introduce a new Engine API method specifically designed for the required reset behavior.
- **Option 4 (Modify EL FCU behavior):** Change the Execution Layer's `forkChoiceUpdated` behavior to meet the specific needs.
The current understanding is that `FCU` does not move the unsafe head back to a canonical block on `op-geth`, leading to confusion on how it previously functioned.
