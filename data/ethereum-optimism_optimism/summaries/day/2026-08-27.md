## CLOSED ISSUES

### Supernode Interoperability and Stability
The issue concerning `op-supernode` cross-safe wedges after invalid-message replacement [#22325] has been closed. Analysis revealed this was a rare, single occurrence in 7.5 weeks, with the root cause identified as chain 901 rejecting batches due to a parent-hash mismatch. The issue is now linked to an existing oscillation problem rather than a distinct supervisor cross-safety bug.

### Rollup Configuration Leniency
The issue regarding `kona-genesis` silently accepting unknown `rollup.json` keys [#22682] has been closed as "not planned." The leniency was a deliberate design choice to ensure compatibility with older configurations containing retired keys. The discussion explored options for stricter parsing but concluded that the current approach is necessary for migration and backward compatibility.

## NEW ISSUES

### Go Module and Contract Artifact Publishing Problems
Two new issues highlight problems with publishing and consuming Optimism components:
- `op-core/superchain` is unconsumable by downstream Go modules because `superchain-configs.zip` is gitignored and not included in published modules [#22678].
- Contract artifacts are not reliably published for released commits, as the `publish-artifacts.sh` script appears to be run manually rather than by CI [#22679].

### Kona Node Stability and Configuration Issues
Several new issues point to potential stability and configuration problems within the Kona node:
- A `kona-node` sequencer can get stuck in a `forkchoiceUpdated -38002` loop after derivation force-includes a block off its unsafe chain [#22681].
- Kona's fork-activation-block predicates use two inequivalent ways to determine activation, based on parent timestamp [#22683].
- `kona-engine`'s `test_chain_label_metrics` installs a global metrics recorder, breaking plain `cargo test` runs [#22687].

### Developer Experience and Tooling Challenges
New issues also address developer experience and tooling:
- `docker buildx bake op-deployer` and `cannon` cannot be built without a private-registry login, due to basing on `dhi.io/alpine-base:3.23` [#22689].
- `alloy-op-evm`'s Canyon create2-deployer activation check hardcodes a 2-second block time [#22684].
- `op-reth`'s pending block environment uses `parent.timestamp + 12` (L1 slot time) on OP chains [#22685].
- `op-reth`'s `--all-features test/lint` runs exit with an error on hosts without an invariant TSC (tracy) [#22688].

### SuperchainERC20 Compatibility Gap
A new issue highlights that there is no supported way for developers to check if a token address is SuperchainERC20 compatible [#1020]. This capability was previously provided by `superchainerc20-compatibility`, which is slated for archiving.

## ACTIVE ISSUES

### Kona Node Network Actor Stalling
Discussion on [#22646] regarding `kona-node`'s `NetworkActor` stalling the p2p swarm during remote-signer HTTP calls continues. A developer has expressed interest in picking up the issue, asking for clarification on overflow policy and whether a proposed deadline fix could be landed separately. The developer plans to measure the degraded case against a signer with injected latency.

### Starter Examples Documentation Audit
The audit of documentation references for starter examples [#1014] is complete. The key finding is that no live documentation links any of the six starter repos or the four archive-sweep repos, meaning archiving will not break published docs. The issue also identified three external README references that need fixing.

### Starter Examples Consolidation
Analysis for consolidating starter examples into a single repository [#1015] suggests consolidating five `superchain-starter*` repos into `superchain-starter`, while leaving `superchainerc20-starter` independent due to its distinct nature and popularity. The recommended approach is a plain copy with pointers to originals for history preservation. The main blockers are write access to the non-target repos and org admin for archiving.

### Archive Sweep for Abandoned Repos
The inbound-link check for abandoned and dead-since-2024 repos [#1017] is complete. No live documentation links any of the four repos slated for archiving. The issue identified two README edits needed in other repos. The `superchainerc20-compatibility` repo's purpose was reconstructed, revealing it provided SuperchainERC20 compliance checks, a capability now logged as a separate issue [#1020]. The main blocker for archiving is organizational admin permissions.

### SuperchainERC20 Compatibility Checking
The newly opened issue [#1020] discusses the lack of a supported way to check SuperchainERC20 compatibility. A comment highlights that the mint/burn checks in the `superchainerc20-compatibility` repo (slated for archiving) might become relevant again if [#22259] (reviving `SuperchainTokenBridge` and `SuperchainERC20`) merges. The priority of this issue is raised due to the importance of token interop for Ink and the potential for confusion regarding token compatibility. The suggested sequencing is to hold this issue until [#22259] resolves.
