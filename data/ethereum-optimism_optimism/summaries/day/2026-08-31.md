# ethereum-optimism/optimism Daily Update (Aug 31, 2026)
## OVERVIEW 
Today's development focused on refining the Super ZK dispute game, enhancing `op-challenger`'s capabilities for super-root game input derivation, and adjusting `kona-sp1` auction defaults. Several new pull requests were opened, addressing dependency updates, documentation, and `op-node` improvements.

## KEY TECHNICAL DEVELOPMENTS

### Super ZK Dispute Game Enhancements
Significant work was done to remediate internal review findings for the Super ZK dispute game. This included adding a solvency invariant and a migration boundary test for `ZKDisputeGame`, and bounding ZK durations within `OPContractsManagerStandardValidator` and `op-deploy`. These changes improve the robustness and security of the dispute game.
[#22328](https://github.com/ethereum-optimism/optimism/pull/22328)

### `op-challenger` and `op-deployer` Updates
The `op-challenger` now supports deriving super-root game inputs directly from `op-node` when a supernode is not set, simplifying the process of exercising super-root prestates. Additionally, `op-deployer` was updated to reflect the `op-contracts/v8.0.0-rc.3` standard versions by bumping the `superchain-registry` dependency.
[#22642](https://github.com/ethereum-optimism/optimism/pull/22642), [#22703](https://github.com/ethereum-optimism/optimism/pull/22703)

### `kona-sp1` Auction Default Adjustment
The default price ceiling for `kona-sp1` proof requests was raised to ensure bids are drawn, addressing an issue where production proof requests remained unfulfilled due to low default pricing compared to the network's clearing price.
[#22640](https://github.com/ethereum-optimism/optimism/pull/22640)

## ACTIVE ISSUES

### `op-core/superchain` Consumability by Downstream Go Modules
The discussion on [#22678](https://github.com/ethereum-optimism/optimism/issues/22678) continues to explore solutions for `op-core/superchain`'s unconsumability by downstream Go modules due to `superchain-configs.zip` being gitignored. The latest comments from sebastianst and geoknee provide detailed analysis and potential directions:
- **Git LFS is not an option:** sebastianst clarifies that `git-lfs` is not viable for Go modules as `cmd/go` builds from raw git data and `proxy.golang.org` does not run lfs smudge, leading to pointer files instead of actual content and `sumdb` verification failures. Committing the zip directly is presented as the only in-repo solution.
- **Import-graph measurement:** sebastianst's analysis shows that a significant number of monorepo packages (206 of 560) currently reach the `superchain-configs.zip` bundle, with nearly half being accidental. Proposed solutions include splitting the `FromRegistry` loader from `DependencySet` types, deleting unused code, and clearing flags/config packages from various `op-` components. These changes could reduce the number of packages reaching the bundle to around 109.
- **Cost of committing the zip:** geoknee's earlier comment quantifies the cost of committing the zip, noting that `op-geth` already tracks its copy (3.9 MB) and that the marginal cost of one bump is approximately 245 KB. The total annual cost for this repo's bump rate would be around 3 MB/year, which is significantly less than what "`.git` growth" might suggest.
- **Loose files vs. zip:** geoknee also compares loose files to a zip, finding minimal difference in `.git` size for consecutive versions, but noting that loose files would offer more reviewable diffs.
- **Submodule limitations:** It's reiterated that embedding directly from the `superchain-registry` submodule does not work due to `//go:embed` limitations and submodules not being included in published module zips.
- **Reducing package reach:** Both sebastianst and geoknee emphasize the importance of reducing the number of packages that reach the bundle, even if the zip shipping decision remains. This includes fixing accidental dependencies and adding `depguard` tests to prevent new ones.
- **Upcoming PRs:** sebastianst mentions an incoming PR stacked on [#22700](https://github.com/ethereum-optimism/optimism/pull/22700) that will address depset splitting, dead-code deletion, and extend the `depguard` test. This includes [#22709](https://github.com/ethereum-optimism/optimism/pull/22709) and [#22712](https://github.com/ethereum-optimism/optimism/pull/22712).
