# ethereum-optimism/optimism Daily Update (Feb 24, 2026)

## OVERVIEW 
Today's development focused on enhancing fault proof testing, integrating the Karst hard fork, and improving CI/CD processes. Key updates include new fault proof tests, a policy engine for staking, and fixes for supernode shutdown issues.

## KEY TECHNICAL DEVELOPMENTS

### Fault Proof System Enhancements & Testing
Significant progress was made in strengthening the fault proof system. This includes porting the `TestInteropFaultProofs_UnsafeProposal` test to devstack, with challenger subtests currently skipped pending supernode support for unsafe super roots ([#19254](https://github.com/ethereum-optimism/optimism/pull/19254)). Additionally, a missing consolidate step case was added to `op-acceptance-tests` for both valid and invalid scenarios, improving coverage for `TestPreInteropFaultProofs` and `TestInteropFaultProofs` ([#19296](https://github.com/ethereum-optimism/optimism/pull/19296)). The timeout for `TestSupernodeInteropActivationAfterGenesis` was also increased to 5 minutes to address flakiness in the merge queue ([#19297](https://github.com/ethereum-optimism/optimism/pull/19297)).

### Superchain Infrastructure & Hard Fork Integration
The Karst hard fork activation logic was added, following the pattern of previous upgrades, though the `superchain.go` line is commented out pending an `op-geth HardforkConfig` update ([#19250](https://github.com/ethereum-optimism/optimism/pull/19250)). Furthermore, capability interfaces were introduced to `op-devstack` to enable polymorphic lookups across component types, marking Phase 3 of the ID type system refactor ([#18874](https://github.com/ethereum-optimism/optimism/pull/18874)). A new `PolicyEngineStaking` periphery contract was also introduced to enable stake-aware transaction ordering in `op-rbuilder` ([#19192](https://github.com/ethereum-optimism/optimism/pull/19192)).

### CI/CD and Supernode Stability Improvements
Efforts were made to enhance CI/CD reliability and supernode stability. Incremental compilation was disabled for all Rust CI jobs by setting `CARGO_INCREMENTAL=0`, which reduces cache size and improves reproducibility. The Rust build cache version was also bumped from 15 to 16 to invalidate stale caches ([#19278](https://github.com/ethereum-optimism/optimism/pull/19278)). A critical fix was implemented to prevent supernode hangs on shutdown by ensuring the metrics service always decrements, addressing a known issue causing tests to hang ([#19293](https://github.com/ethereum-optimism/optimism/pull/19293)).

An issue was opened regarding the `op-reth` `p2p::can_sync` test, which is currently ignored due to a SIGABRT crash caused by an incorrect `debug_assert!` in upstream reth v1.11.1 ([#19298](https://github.com/ethereum-optimism/optimism/issues/19298)).

### `op-proposer` Sepolia Devnet Anomaly
A bug was reported where the `op-proposer` on the Sepolia devnet uses a timestamp as `rootBlockNumber` in the `anchorStateRegistry`, leading to `UnexpectedRoot` claim checks firing ([#19301](https://github.com/ethereum-optimism/optimism/issues/19301)).

## ACTIVE ISSUES
### `op-batcher` Post-Holocene Ordering
The issue [#18507](https://github.com/ethereum-optimism/optimism/issues/18507) describes `op-batcher` failing to account for post-Holocene ordering in concurrent mode. A recent comment by kien-rise links this issue to [#13169](https://github.com/ethereum-optimism/optimism/pull/13169), suggesting a potential relation to a pull request.

### `op-supernode` Superroot SLA Updates
Issue [#19180](https://github.com/ethereum-optimism/optimism/issues/19180) discusses the ill-defined and currently misbehaving SLA of the Superroot object. The expectation is that a super root should be provided whenever output roots for all chains are available. Recent comments from ajsutton note that in [#19302](https://github.com/ethereum-optimism/optimism/pull/19302), some tests (`fpp_test.go` - `TestNextSuperRootNotFound` and `interop_fault_proof_tests.go` - `TestInteropFaultProofs`) had to be skipped due to missing partial `OptimisticAtTimestamp` data. axelKingsley added that Optimistic Roots should be a best-attempt by all, with unavailable roots either excluded or included as empty values.
