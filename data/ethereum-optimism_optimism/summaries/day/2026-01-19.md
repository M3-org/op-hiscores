# ethereum-optimism/optimism Daily Update (Jan 19, 2026)
## OVERVIEW 
Today's development focused on refining CI/CD processes, enhancing Foundry versioning policies, and introducing new checks for `op-geth` versions. Several new pull requests were opened, addressing fixes, features, and dependency updates.

## KEY TECHNICAL DEVELOPMENTS

### CI/CD and Artifact Management Improvements
Improvements were made to the CI/CD pipeline to optimize artifact downloads and introduce new checks. A change was implemented to avoid fallback downloads of artifacts when not on the `develop` branch, streamlining the build process ([#18785](https://github.com/ethereum-optimism/optimism/pull/18785)). Additionally, a new CI check was added to validate that the `go.mod` replace directive points to a valid `op-geth` tag, enhancing version control and stability ([#18854](https://github.com/ethereum-optimism/optimism/pull/18854)).

### Foundry Versioning and Policy Enforcement
A new Foundry Versioning Policy was introduced to standardize and manage upgrades of Foundry tools ([#18804](https://github.com/ethereum-optimism/optimism/pull/18804)). To enforce this, a Graphite prompt was added to detect Foundry dependency bumps in pull request reviews, requiring an approved design document for such changes ([#18851](https://github.com/ethereum-optimism/optimism/pull/18851)).

## ACTIVE ISSUES

### `op-reth` and `op-geth` P2P Connection Flakiness
Discussion on [#18570](https://github.com/ethereum-optimism/optimism/issues/18570) continues regarding the flakiness of `op-reth` <-> `op-geth` P2P connections in system tests. A new pull request related to this issue has been created and is awaiting review. Previously, the issue was classified as a major bug due to its impact on test stability and potential production compatibility. The core problem lies in the `admin_peers` encoding results and the differences in P2P implementations between `op-reth` and `op-geth`.

### `op-supernode` Reset Handling
The discussion on [#18740](https://github.com/ethereum-optimism/optimism/issues/18740) focuses on the reset handling mechanism within `op-supernode`. The latest comment highlights prior art from `op-wheel` and `op-node`. While `op-node` uses `forkChoiceUpdate` (FCU) triggered by `op-supervisor` to reset local fork choice state, there's confusion as experience and source code tests suggest FCU might not move the unsafe head back to a canonical block on `op-geth`.

### `op-reth` Batcher Throttling
Regarding [#18764](https://github.com/ethereum-optimism/optimism/issues/18764), the latest comment indicates that for `op-reth`, both throttling mechanisms appear to be implemented in the payload builder. However, no testing related to this implementation has been found so far. This issue concerns the batcher-sequencer throttling mechanism, which is crucial for managing data availability size.
