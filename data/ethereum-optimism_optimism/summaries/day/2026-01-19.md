## ACTIVE ISSUES

### op-supernode: Reset Handling [#18740]
Discussion continues on how to handle resets in `op-supernode`. The latest comments from @axelKingsley and @geoknee explore several options:
1.  **Hack around FCU behavior**: This involves updating to a synthetic block and then back to the desired block, which is currently the preferred short-term solution.
2.  **Supernode-driven resets**: Making supernode-driven resets behave like regular pre-interop reorgs. This is considered less feasible with the new supernode design.
3.  **New engine API method**: Adding a new method to ELs to perform the required reset. This is a long-term preference.
4.  **Modify EL FCU behavior**: Changing the existing FCU behavior to meet the requirements.
There is confusion regarding how FCU previously worked, as current tests show it doesn't move the unsafe head back to a canonical block on `op-geth`.

### op-reth: batcher throttling [#18764]
@einar-oplabs provided an update on `op-reth`'s batcher throttling mechanisms. `op-reth` implements both throttle mechanisms in its payload builder, but without dedicated tests. In contrast, `op-rbuilder`'s payload builder includes several tests for data availability and block/transaction size limits.

### chore(sysgo/p2p): fix op-reth <-> op-geth connection flakiness [#18570]
@forkfury submitted a pull request related to this issue, which @theochap is invited to review. Previously, @rdin777 highlighted the critical nature of this bug, affecting test stability and potential production compatibility, and suggested it be classified as a high-priority chore. The issue stems from a failing check in `l2_el_p2p_util.go` for presets mixing `op-geth/op-reth` nodes or multiple `op-reth` nodes, indicating a problem with `admin_peers` encoding results.
