# ethereum-optimism/design-docs Weekly Report (Jan 18 - 24, 2026)

## 🚀 Highlights
This week focused on refining the technical architecture of the Superchain, with a particular emphasis on node stability and cross-client interoperability. Key efforts centered on resolving P2P connection flakiness between `op-reth` and `op-geth`, alongside deep architectural discussions regarding reset handling for the `op-supernode`. The addition of a new Foundry upgrade template also signals a continued commitment to improving the developer experience by providing standardized tooling for protocol upgrades.

## 🛠️ Key Developments

### Developer Tooling & Templates
To streamline the process of protocol upgrades and smart contract management, a new Foundry upgrade template was integrated into the repository. This resource provides a standardized framework for developers working within the Optimism ecosystem.
*   **Foundry Upgrade Template:** Added a new template to the `assets` directory to support development workflows ([#362](https://github.com/ethereum-optimism/design-docs/pull/362)).

### Protocol Infrastructure & Client Stability
Significant technical analysis was directed toward the performance and reliability of various OP Stack client implementations.
*   **Batcher Throttling in op-reth:** Developers compared the payload builder implementations between `op-reth` and `op-rbuilder`. While `op-reth` has implemented throttle mechanisms, it currently lacks the robust data availability and block size limit testing found in `op-rbuilder`.
*   **P2P Connectivity:** Work progressed on addressing instability between `op-reth` and `op-geth` nodes, with active PRs being tracked to resolve connection flakiness ([#18570](https://github.com/ethereum-optimism/design-docs/issues/18570)).

## 🐛 Issues & Triage

### New & Active Issues
The week was dominated by complex architectural discussions regarding how the Supernode interacts with the Engine API.
*   **Supernode Reset Handling ([#18740](https://github.com/ethereum-optimism/design-docs/issues/18740)):** A major discussion is underway regarding how `op-supernode` handles resets. Current findings suggest that `engine_forkChoiceUpdatedV1` may not reliably reset the unsafe head to a canonical block on `op-geth`. Three potential paths are being evaluated:
    1.  Implementing workarounds for existing Fork Choice Updated (FCU) behavior.
    2.  Treating supernode-driven resets as standard reorganizations.
    3.  Proposing a new Engine API method to handle these cases explicitly.
*   **Client Parity:** Ongoing discussions regarding `op-reth` highlight a need for increased test coverage to match the standards set by other payload builder implementations ([#18764](https://github.com/ethereum-optimism/design-docs/issues/18764)).

## 💬 Community & Collaboration
Collaboration this week was characterized by deep technical peer review between OPLabs engineers and protocol contributors. The dialogue surrounding the `op-supernode` reset handling (involving contributors like geoknee and einar-oplabs) demonstrates a highly analytical approach to solving edge cases in the Engine API. Furthermore, the cross-client work involving `op-reth` and `op-geth` shows active coordination to ensure the Superchain remains client-agnostic and resilient.
