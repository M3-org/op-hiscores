# ethereum-optimism/design-docs Weekly Report (Jan 25 - 31, 2026)

## 🚀 Highlights
This week focused on refining the protocol's deployment and configuration infrastructure, specifically regarding the integration of OPCMv2 and post-Holocene gas management. Significant progress was made in documenting security specifications and providing developer guidance for system configuration changes. While the team faced challenges with acceptance testing on the Glamsterdam devnet due to L1 compatibility issues, these hurdles have informed a clear roadmap for improving custom L1 support. Overall, the week's activity centered on stabilizing the Superchain's deployment tooling and preparing for upcoming sequencer-defined metering benchmarks.

## 🛠️ Key Developments

### Protocol Security & OPCMv2 Integration
The protocol's security documentation was strengthened with the addition of a Failure Mode Analysis (FMA) for OPCMv2. This addition ensures that the security specifications remain up-to-date as the protocol evolves.
*   **OPCMv2 FMA:** Added comprehensive security documentation for OPCMv2 ([#364](https://github.com/ethereum-optimism/design-docs/pull/364)).

### Gas Configuration & Deployment Tooling
Efforts were concentrated on aligning deployment tools with recent hardfork requirements, particularly regarding gas limits and system configurations.
*   **Post-Holocene Gas Guide:** Published a technical guide detailing how to modify gas configuration values on the system config following the Holocene upgrade ([#1944](https://github.com/ethereum-optimism/design-docs/issues/1944)).
*   **Sequencer-Defined Metering:** The scope for the Sequencer-Defined Metering design doc was expanded to include the initial Proof of Concept (PoC). This work is a prerequisite for the design evaluation and benchmarking scheduled for late January ([#360](https://github.com/ethereum-optimism/design-docs/issues/360)).

## 🐛 Issues & Triage

### Closed Issues
*   **Acceptance Testing:** The dry run of acceptance tests against `bal-devnet-1` was concluded. Although the run identified issues with unsupported custom L1 setups and inconsistent RPC responses, it provided critical data for fixing custom L1 support in future iterations ([#18755](https://github.com/ethereum-optimism/design-docs/issues/18755)).
*   **Documentation:** Successfully closed the tracking issue for the gas configuration guide after its publication ([#1944](https://github.com/ethereum-optimism/design-docs/issues/1944)).

### New & Active Issues
*   **OPCMv2 Expansion:** A new initiative was launched to expand OPCMv2 support beyond the `op-deployer` package to ensure full integration across the stack ([#18942](https://github.com/ethereum-optimism/design-docs/issues/18942)).
*   **Deployment Blockers:** The `op-deployer` (v0.2.6) is currently facing "transaction gas limit too high" errors due to Fusaka hardfork enforcement. Developers are investigating whether `v0.5.0*` resolves these issues for alt-da configurations ([#17912](https://github.com/ethereum-optimism/design-docs/issues/17912)).
*   **Batcher Synchronization:** Ongoing debate persists regarding how `op-batcher` should handle rollup config updates. A new proposal suggests treating an outdated config as a critical error to force a process restart, ensuring the batcher stays in sync with the `op-node` ([#18178](https://github.com/ethereum-optimism/design-docs/issues/18178)).

## 💬 Community & Collaboration
The week's activity highlights a strong collaborative effort between protocol engineers and tool developers to resolve friction points in the deployment pipeline. Discussions around `op-batcher` synchronization and `op-deployer` gas limits show an active feedback loop regarding how hardforks (Holocene and Fusaka) impact existing infrastructure. The transition from the failed Glamsterdam devnet dry run to a concrete plan for L1 support improvements demonstrates a transparent and iterative approach to protocol testing and development.
