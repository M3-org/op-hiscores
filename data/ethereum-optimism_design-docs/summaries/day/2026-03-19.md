### Initial EL Sync UX and Correctness ([#17631](https://github.com/ethereum-optimism/design-docs/issues/17631))
Discussion continued on the correctness and user experience of the op-node's initial EL sync. The core issue is that after initial EL sync, the safe and finalized heads are incorrectly set to the unsafe head, rather than reflecting the L1 finalization gadget.

- **Correctness vs. UX Trade-offs:**
    - Setting safe/finalized to genesis is simplest but requires long derivation time.
    - Setting safe/finalized to "unsafe head minus sequencer window" (e.g., 12 hours) balances correctness with improved UX by reducing derivation time.
    - Allowing external sources for safe/finalized offers best UX but adds complexity and trust assumptions.
- **Proposed Solution:** Option 2 (unsafe head minus sequencer window) is seen as a reasonable balance, though the node will still need time to derive forward to the L1-dictated safe/finalized tip.

### Review kona-interop block hash oracle ([#18288](https://github.com/ethereum-optimism/design-docs/issues/18288))
The discussion focused on ensuring the `kona-interop` block hash oracle is properly tested, particularly for looking up blocks prior to the current history window.

- **Integration Testing:** The main goal is to have an integration/acceptance test that verifies the ability to look up old block hashes using `op-supernode` instead of `op-supervisor`.
- **Test Strategy:** Moving the existing action test to an acceptance test is suggested. Utilizing `presets.WithTimeTravelEnabled()` and `sys.AdvanceTime` in `op-acceptance-tests` could generate sufficient chain history for such a test, even though current time-travel tests don't typically wait for L2 catch-up after L1 time travel.

### Non-terminating CI job: memory-all-opn-op-geth ([#19563](https://github.com/ethereum-optimism/design-docs/issues/19563))
This issue tracks a recurring problem where the `memory-all-opn-op-geth` CI job hangs indefinitely. Multiple occurrences were reported today, with detailed root cause analysis provided.

- **Root Cause Identified:** A mutex deadlock in `VirtualNode` during shutdown was identified. This occurs when `VirtualNode.Start()` holds a mutex while calling `OpNode.Stop()`, which in turn waits for the event system to drain. The event system's `GlobalSyncExec.Drain` then tries to acquire the same mutex, leading to a deadlock.
- **Flakiness Explanation:** The deadlock is timing-dependent, occurring only when the event system is processing a specific event that calls `SyncStatus()` at the precise moment `Start()` acquires the mutex.
- **Proposed Fix:** A fix PR has been created to release the mutex before calling `inner.Stop()` and to add a defensive timeout to `Supernode.Stop()`.
- **Related Flakes:** Other flaky tests (`TestChallengerPlaysGame`, `TestProposer`) within the `interop/proofs` package were also identified as contributing to the job hanging, with separate issues and fixes proposed for them.
