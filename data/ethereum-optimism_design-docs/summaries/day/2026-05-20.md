## ACTIVE ISSUES
### Flaky Test Investigations
Discussions continued on several flaky test issues. For `TestFollowL2_ReorgRecovery` [#19967](https://github.com/ethereum-optimism/design-docs/issues/19967), the test resurfaced with a different failure signature (sequencer RPC deadline) but likely the same underlying timing/sync issue. The root cause analysis and fix were previously identified in PR #20651.

Regarding `FuzzEncodeDecodeBlob` [#20935](https://github.com/ethereum-optimism/design-docs/issues/20935), the root cause was identified as `Blob.FromData` formatting an entire payload into its `ErrBlobInputTooLarge` error, leading to large error strings and the fuzzing process hanging. A fix has been drafted in PR #20940.

For `FuzzDetectNonBijectivity` [#20936](https://github.com/ethereum-optimism/design-docs/issues/20936), the flakiness was attributed to the fuzz target capturing `*rand.Rand` outside the `f.Fuzz` closure, causing non-determinism. A fix has been drafted in PR #20939, deriving `byteToFlip`/`bitToFlip` from `sha256.Sum256(d)` to preserve coverage quality.

### op-reth Bootstrap Incompatibility
An issue regarding `op-reth` minimal Bedrock bootstrap being incompatible with storage v2 was actively discussed [#20821](https://github.com/ethereum-optimism/design-docs/issues/20821). A user reported attempting to reproduce the issue and provided logs showing a successful `init-state` and node launch without the reported panic, indicating further investigation is needed.

### `debug_executePayload` Requirement
The investigation into whether `debug_executePayload` and related crates can be removed concluded that it is not removable as dead code [#20879](https://github.com/ethereum-optimism/design-docs/issues/20879). It is an active, opt-in fast-path with a maintained server implementation in `op-reth`, crucial for `op-reth` to work as a source for `kona-proofs` and for fault-proof witness prefetching. The "experimental" label signifies an opt-in optimization with a canonical fallback, not a lack of maturity.

### op-supernode Backfill Depth Logic
An issue concerning `op-supernode` ignoring backfill depth if the activation timestamp is not set was closed today [#20892](https://github.com/ethereum-optimism/design-docs/issues/20892). A pull request [#20895](https://github.com/ethereum-optimism/optimism/pull/20895) was submitted to address this, aiming to fix the behavior where `op-supernode` fails to start under these conditions.
