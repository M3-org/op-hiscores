# ethereum-optimism/design-docs Daily Update (Apr 23, 2026)
## OVERVIEW 
Today saw the opening of a new pull request to enable CircleCI for fork PRs. Two issues were closed, including one related to deprecating req-resp p2p sync and another addressing a flaky test. New issues were opened concerning sequencer LightCL behavior and a transient EL dial timeout.

## KEY TECHNICAL DEVELOPMENTS

## NEWLY OPENED PULL REQUESTS
- A new pull request, [#377](https://github.com/ethereum-optimism/design-docs/pull/377), was opened to enable CircleCI for fork PRs, aiming to improve CI coverage for contributions from forks.

## CLOSED ISSUES

- **Deprecation of Req-Resp P2P Sync:** The issue [#14108](https://github.com/ethereum-optimism/design-docs/issues/14108) concerning the removal of req-resp p2p sync in `op-node` was closed. This issue aimed to address sync problems with the old protocol, with discussions highlighting the benefits of alternative unsafe block sync mechanisms. The issue was closed in favor of a new issue in the protocol-team repository.
- **Flaky Test Resolution:** The issue [#20254](https://github.com/ethereum-optimism/design-docs/issues/20254), reporting a flaky `TestRelayWithInvalidMessagesSteady` due to transient EL dial timeouts, was closed. A draft fix was opened in the `optimism` repository, identifying the root cause as the sampler goroutine not tolerating `*net.OpError` and proposing a fix to warn and continue on non-context errors.

## NEW ISSUES

- **Sequencer LightCL Engine Reset:** A new issue, [#20294](https://github.com/ethereum-optimism/design-docs/issues/20294), was opened to address a problem where an `op-node` configured as a "sequencer LightCL" performs a needless engine reset on every restart, which may rewind EL heads.
- **Flaky Test: Transient EL Dial Timeout:** A new issue, [#20254](https://github.com/ethereum-optimism/design-docs/issues/20254), was opened by Claude (AI assistant) regarding a flaky `TestRelayWithInvalidMessagesSteady` due to a transient EL dial timeout.

## ACTIVE ISSUES

- **Kona-Interop Block Access Review:** Discussion on [#19266](https://github.com/ethereum-optimism/design-docs/issues/19266) continues regarding the review of access to internally created blocks during Kona-proofs interop validation. The latest comments confirm that deposit-only block receipts should be available from the canonical chain. A related issue was discovered where, during block replacement, generated receipts are not stored, potentially causing consolidation failures if other messages reference the deposit-only block. A test has been created to confirm this behavior.
