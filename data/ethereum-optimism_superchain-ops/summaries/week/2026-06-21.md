# ethereum-optimism/superchain-ops Weekly Report (Jun 21 - 27, 2026)

## 🚀 Highlights
This week, development activity centered on critical infrastructure maintenance and the ongoing migration of Ink Sepolia to OP Enterprise. Key operations included the rotation of signers for Foundation Upgrade and Operations safes to maintain protocol security and the proposal of gas limit resets for both OP Mainnet and Ink Sepolia. While some work on interoperability recovery runbooks faced minor delays due to resource allocation, the team successfully streamlined the proving cluster service requirements by prioritizing existing `sp1-cluster` support.

## 🛠️ Key Developments

### Ink Sepolia & OP Enterprise Migration
Significant progress was made on transitioning Ink Sepolia to the OP Enterprise framework. This involved updating operational documentation and configurations to support new infrastructure requirements.
*   Executed README updates for the batcher unsafe signer and proposer rotation as part of the migration process ([#1478](https://github.com/ethereum-optimism/superchain-ops/pull/1478)).

### Security & Governance Operations
The team performed routine but essential security maintenance on core governance infrastructure to ensure the integrity of the Superchain's administrative functions.
*   Proposed the rotation of two signers on the Foundation Upgrade and Operations safes (055-058) ([#1479](https://github.com/ethereum-optimism/superchain-ops/pull/1479)).

### Network Optimization (Gas Management)
Maintenance efforts focused on stabilizing network parameters through gas limit resets across both testnet and mainnet environments.
*   Opened pull requests to reset the Karst gas-limit for **OP Mainnet** ([#1480](https://github.com/ethereum-optimism/superchain-ops/pull/1480)) and **Ink Sepolia** ([#1481](https://github.com/ethereum-optimism/superchain-ops/pull/1481)).

## 🐛 Issues & Triage

### Closed Issues
*   **Proving Cluster Service:** The requirement for a dedicated proof request/queue service for self-hosted clusters was evaluated and closed. It was determined that current support for `sp1-cluster` is sufficient for immediate SP-1 needs, reducing unnecessary architectural overhead ([#21462](https://github.com/ethereum-optimism/superchain-ops/issues/21462)).

### Active Issues & Discussions
*   **Rust Stack Release Process:** Discussions are ongoing regarding the adaptation of the Rust stack release process to the monorepo structure. A specific concern was raised regarding the `op-revm` changelog, which is currently outdated (stopping at `19.0.0`) despite newer versions being available on crates.io. This highlights a need for better per-version documentation ([#18926](https://github.com/ethereum-optimism/superchain-ops/issues/18926)).
*   **Invalid Interop Message Recovery:** Work on the runbook for recovering chains after invalid interop messages—which currently trigger unhandled large reorgs—has been delayed by approximately one week due to competing project priorities ([#21161](https://github.com/ethereum-optimism/superchain-ops/issues/21161)).

## 💬 Community & Collaboration
The week's activity demonstrated a strong focus on cross-team coordination, particularly regarding the alignment of the Rust stack with monorepo standards. Technical discussions in the issues tracker, such as those involving `anaPerezGhiglia` on changelog standards and `jelias2` on interop recovery, reflect a transparent approach to managing technical debt and resource constraints. The collaboration remains focused on maintaining high standards for developer experience through accurate documentation and robust recovery procedures.
