## ACTIVE ISSUES

### `op-geth` Decoupling: `op-service/sources` as OP-aware eth client
Discussion on [#20264](https://github.com/ethereum-optimism/superchain-ops/issues/20264) revealed a design correction for the `op-batcher` migration. It was determined that `op-batcher` cannot migrate to `InfoAndUserTxs` and will instead go payload-native. This is because `InfoAndUserTxs` drops critical information required for batch building, such as the L1-info deposit and post-exec transactions. The batcher will now fetch `*eth.ExecutionPayloadEnvelope` via `PayloadByNumber`. Additionally, `optypes.Receipts` root derivation needs to handle three distinct OP arms for receipts, and `FetchReceipts` must derive transaction hashes from raw transactions.

### Flaky `reth-optimism-node` Integration Test
Extensive analysis on [#20973](https://github.com/ethereum-optimism/superchain-ops/issues/20973) regarding the `peers_negotiate_eth_69` SIGSEGV flake in `reth-optimism-node` integration tests was provided. Experimental verification refuted the previously suspected "detached payload thread polls a torn-down runtime" mechanism. The actual cause of the segfault remains unidentified, and the proposed "own-runtime patch" is not being pursued as a fix. The recommended next step is to capture a core dump/faulting stack in CI to definitively identify the mechanism.

### Flaky `TestSupernodeLightSequencerInteropInvalidMessageReplacement`
The recurring flake in `TestSupernodeLightSequencerInteropInvalidMessageReplacement` ([#21635](https://github.com/ethereum-optimism/superchain-ops/issues/21635)) was discussed, with a root cause identified and a fix proposed. The flake occurs because `FollowSource` can canonicalize an upstream block while the light sequencer still has a timer armed against a previous block, leading to stale parent issues and `Invalid payload attributes`. A draft PR ([ethereum-optimism/optimism#21913](https://github.com/ethereum-optimism/optimism/pull/21913)) aims to reject non-derived build starts unless their parent block ID matches the engine controller's current unsafe block ID, thereby preventing stale Engine API calls. The fix has undergone extensive verification and adversarial review.
