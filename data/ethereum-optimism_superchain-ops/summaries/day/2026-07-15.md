# ethereum-optimism/superchain-ops Daily Update (Jul 15, 2026)
## OVERVIEW 
The day saw significant activity in refining OPCM V800 templates and addressing critical issues related to brotli decompression and test flakiness. Discussions on `op-proposer` source selection and `op-reth-test-engine` development also progressed.

## KEY TECHNICAL DEVELOPMENTS

- **OPCM V800 Template Refinements:** New pull requests were opened to re-add OPCM V800 templates with simplified super-permissioned arguments, following an earlier removal due to premature merging. This indicates ongoing work to streamline and improve the configuration of dispute games. [#1502](https://github.com/ethereum-optimism/superchain-ops/pull/1502), [#1501](https://github.com/ethereum-optimism/superchain-ops/pull/1501), [#1500](https://github.com/ethereum-optimism/superchain-ops/pull/1500)

## NEWLY OPENED PULL REQUESTS
- **Feature: Re-add OPCM V800 templates:** A new pull request, [#1502](https://github.com/ethereum-optimism/superchain-ops/pull/1502), was opened to re-introduce OPCM V800 templates with simplified super-permissioned arguments. This follows a previous pull request, [#1501](https://github.com/ethereum-optimism/superchain-ops/pull/1501), which removed these templates due to being merged too early. Additionally, [#1500](https://github.com/ethereum-optimism/superchain-ops/pull/1500) aims to fix and simplify OPCM V800 super permissioned game arguments.

## CLOSED ISSUES

- **Kona Host Game Input and Witness Generation Review:** Issue [#18430](https://github.com/ethereum-optimism/superchain-ops/issues/18430), concerning the review of host game input and witness generation for soundness, was closed. This issue was tracked in a separate issue, and a TODO referencing it will be updated.
- **Kona Brotli Decompression Protocol Adjustment:** Issue [#20666](https://github.com/ethereum-optimism/superchain-ops/issues/20666), which proposed switching `decompress_brotli` to `BrotliDecompressCustomIoCustomDict` for incremental-flush parity with `op-node`, was closed as "won't-fix." Differential testing revealed that the current eager decoder never lags `op-node`, and the proposed change would slightly reduce parity.

## NEW ISSUES

- **Kona Brotli Decoder Leniency:** A new issue, [#21793](https://github.com/ethereum-optimism/superchain-ops/issues/21793), was opened to address the fact that the `brotli-decompressor` used in Kona is more lenient than `op-node`'s `andybalholm` decoder, accepting malformed channels that `op-node` rejects. This divergence could lead to consensus issues.

## ACTIVE ISSUES

- **Flaky Test: `TestExecutePayloadSuccess` ([#19898](https://github.com/ethereum-optimism/superchain-ops/issues/19898))**: The issue was reopened due to the recurrence of a proofs ExEx store readiness race in `TestL2MultipleTransactionsInSingleBlock`. The previous fix was insufficient as it only checked the validator's EL head, not the asynchronously populated proofs ExEx store. A new fix, [#21807](https://github.com/ethereum-optimism/superchain-ops/pull/21807), addresses this by waiting for the later of both receipt blocks before fetching proofs, ensuring the ExEx store is ready.

- **`op-reth-test-engine`: minimal in-test EL for `op-e2e/actions` ([#20415](https://github.com/ethereum-optimism/superchain-ops/issues/20415))**: The `op-reth-test-engine` is now complete, with the full implementation available as a draft stack. The design was updated to confirm support for FCU-with-attrs and clarify that processed payloads remain non-canonical until an FCU makes them head, aligning with Engine API semantics. Generic subprocess-IPC client plumbing has been moved to a shared `op-service/engineipc` package for reuse.

- **`op-proposer`: select proposal sources by root format instead of interop mode ([#21710](https://github.com/ethereum-optimism/superchain-ops/issues/21710))**: Discussions are ongoing regarding how `op-proposer` classifies proposal sources. An implementation, [#21778](https://github.com/ethereum-optimism/optimism/pull/21778), was proposed but deemed potentially confusing. The current recommendation is to rename CLI options, specifically `--supernode-rpc` to `--superroot-rpc`, to make the user's intent more explicit.
