### `op-node`: On the Initial EL Sync UX and Correctness ([#17631](https://github.com/ethereum-optimism/superchain-ops/issues/17631))
Discussions continued regarding the `op-node`'s behavior during initial EL Sync, specifically concerning how it marks the reached target as finalized, potentially leading to a state where the EL considers a block finalized even if it's not.

*   **`trianglesphere`** clarified that the current behavior was the intended design for the EL sync feature, noting that re-running derivation on a snap-synced node is problematic as the node can only execute blocks after snap syncing is complete.
*   **`sebastianst`** acknowledged the current behavior as a bug and suggested that while execution from the EL unsafe head is necessary due to state availability, derivation from a prior L1 block followed by consolidation could verify alignment with the EL-synced unsafe chain. They also proposed fixing the code to only advance the unsafe reference while keeping safe and finalized at genesis, with a plan needed for the transition to the first derived and consolidated safe block.
*   **`axelKingsley`** emphasized that EL sync should only drive to the tip of the chain for content that is truly finalized. They suggested that Snap Sync should follow the finalized L2 as a maximum target, and once snapped, resume full sync, only needing to gossip/derive/consolidate the range from finalization to tip.
*   **`trianglesphere`** responded that while `op-reth` in EL sync could follow the finalized L2 as a maximum target, `op-geth` in snap sync cannot, as snap sync requires state snapshots which `geth` only stores for a limited number of blocks from its tip.
