### Supernode Interop Client Initialization
A new issue [#21136](https://github.com/ethereum-optimism/op-analytics/issues/21136) was opened detailing a problem where `op-supernode` interop activity can get permanently stuck with an "engine client not initialized" error if the execution layer is unreachable at startup, as the connection is never retried. A proposed fix involves decoupling the engine-controller initialization from the virtual node restart loop and guarding `c.engine` with mutexes.

## ACTIVE ISSUES
### Supernode/Reth CL Sync Recovery Stall
Discussion on [#21076](https://github.com/ethereum-optimism/op-analytics/issues/21076) continued with an update from a new A/B test. The issue, where CL sync recovery can stall when SafeDB/bookkeeping references an EL-missing block, was reproduced without `op-supernode`, indicating the immediate failure lies within the `op-node`/`op-reth` CL derive/build Engine API path. The key pattern observed is a half-completed block transition where `Block added to canonical chain` appears, but `Received new payload` and `Canonical chain committed` do not, leading to Engine API timeouts and a frozen latest/queryable state.

### Cross-Safe Backlog After Stall
The issue [#21117](https://github.com/ethereum-optimism/op-analytics/issues/21117), concerning `op-supervisor`/`op-supernode` cross-safe not draining a backlog faster than real-time after a stall, received a comment suggesting that a 12-hour delay in catching up could indicate the sequencing window expired. If the sequencing window expires due to an extended batcher outage, manual intervention is required to recover, as the safe head force-increases every L1 block, invalidating batcher data.
