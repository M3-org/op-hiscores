## ACTIVE ISSUES

### `opgeth-decoupling`: Migrating Tests and L2 Client
Discussions on [#20265](https://github.com/ethereum-optimism/op-geth/issues/20265) and [#20264](https://github.com/ethereum-optimism/op-geth/issues/20264) highlight critical considerations for migrating integration tests and making `op-service/sources` the OP-aware Ethereum client. Key points include:
- **Receipt Index Correlation:** Tests that correlate `txs[i]` with `receipts[i]` by position will break when migrating to `InfoAndUserTxs` due to the exclusion of synthetic transactions. These tests must filter receipts in lockstep or use paired accessors.
- **Lagoon's `0x7D` Post-Exec Tx:** The Lagoon hardfork introduces a trailing `0x7D` post-execution transaction to L2 blocks. Tests assuming the only synthetic transaction is the leading `0x7E` deposit need to be updated to handle both.
- **L2 Transaction Representation:** A design resolution proposes partitioning L2 transaction accessors by transaction class instead of using an `optypes.Transaction` wrapper. This involves adding `InfoAndUserTxs`, `InfoAndDeposits`, and `InfoAndFirstDeposit` to `apis.EthClient` to handle different transaction types.
- **`0x7D` Routing:** Lagoon makes `0x7D` routing load-bearing, as the post-exec tx is a canonical block transaction. Accessors must route both `0x7E` and `0x7D` out for upstream go-ethereum compatibility.

### `opgeth-decoupling`: `op-core/types` and Call-Site Swaps
Discussions on [#20262](https://github.com/ethereum-optimism/op-geth/issues/20262) and [#20263](https://github.com/ethereum-optimism/op-geth/issues/20263) focus on creating `op-core/types` and swapping call-sites across various Optimism services. Key points include:
- **Transition-Only Helpers:** Helper functions like `IsDepositTx` and `SourceHash` that operate on `*types.Transaction` are considered transition scaffolding. They will be deleted after the final cutover to upstream go-ethereum, as upstream `*types.Transaction` cannot hold deposit or post-exec transactions.
- **Durable Shape:** The long-term approach is for callers to decode raw bytes into `optypes.DepositTx` or `optypes.PostExecTx` and read fields directly from the struct.
- **`PostExecTx` as Canonical:** The `PostExecTx` is a canonical block transaction in the Lagoon hardfork, participating in the L2 block transaction list. This reinforces the need for the decode path to handle both `0x7E` and `0x7D` transactions.
- **Call-Site Swap Strategy:** When swapping call sites, prioritize decoding to `optypes.DepositTx` via `UnmarshalDepositTx` and reading struct fields directly, rather than relying on the `*types.Transaction` helpers, if the raw transaction bytes are readily available.
