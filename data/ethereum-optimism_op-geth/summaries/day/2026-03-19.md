## ACTIVE ISSUES

- **Initial EL Sync UX and Correctness** [#17631](https://github.com/ethereum-optimism/op-geth/issues/17631)
  Discussion continued on the correctness and user experience of the initial EL Sync. The core problem is that after initial EL sync, the safe and finalized heads are incorrectly set to the unsafe head, rather than reflecting the L1 finalization gadget. Option 2, setting safe/finalized to the unsafe head minus the sequencer window, was highlighted as a balanced approach for correctness and UX, requiring derivation of approximately 12 hours of data.

- **Review kona-interop block hash oracle** [#18288](https://github.com/ethereum-optimism/op-geth/issues/18288)
  The discussion focused on ensuring an integration/acceptance test exists for looking up block hashes prior to the current history window. It was noted that an existing action test covers this, and the goal is to transition this to an acceptance test using `op-supernode` instead of `op-supervisor`. The challenge lies in generating sufficient chain history for the test, with `presets.WithTimeTravelEnabled()` and `sys.AdvanceTime` in `op-acceptance-test` suggested as potential solutions.

- **Non-terminating CI job: memory-all-opn-op-geth** [#19563](https://github.com/ethereum-optimism/op-geth/issues/19563)
  This issue, which was reopened, continues to be a major focus due to recurring non-terminating CI jobs. A detailed root cause analysis identified a mutex deadlock in `VirtualNode` during shutdown, involving three goroutine groups. The deadlock occurs when the event system processes an event calling `SyncStatus()` while `Start()` acquires a mutex and begins `inner.Stop()`. A fix PR (ethereum-optimism/optimism#19680) has been created to address this by releasing the mutex before calling `inner.Stop()` and adding a defensive timeout to `Supernode.Stop()`. The issue was closed as the fix is believed to resolve the problem.

- **Flaky: TestInteropFaultProofs_ConsolidateValidCrossChainMessage** [#19656](https://github.com/ethereum-optimism/op-geth/issues/19656)
  The root cause for this flaky test was identified as a race condition in `op-service/testutils/tcpproxy/proxy.go`. Specifically, `handleConn` held a mutex while dialing upstream, allowing `Close()` to be called before connections were tracked, leading to untracked goroutines and test hangs. A fix PR (ethereum-optimism/optimism#19662) was created to release the mutex before dialing and check for `p.stopped` before registering connections.
