## ACTIVE ISSUES
- **`op-supernode`/`op-reth` CL Sync Recovery Stalling** [#21076](https://github.com/ethereum-optimism/op-geth/issues/21076):
    - **Summary**: This issue details a problem where CL sync recovery can stall if `SafeDB`/bookkeeping references an EL-missing block.
    - **Latest Observations**: Karlfloersch provided extensive updates, noting that `latest` blocks advanced but `safe`/`finalized` blocks did not. The primary blocker appears to be FCU timeouts from `op-supernode` to `op-reth` Engine API. Reth's CL-health monitor also warned about no consensus updates.
    - **Working Hypothesis**: The issue seems to stem from wiping only the supernode DBs, which makes the verified DB empty while preserving reth's state. This leads to the `SuperAuthority` returning an activation anchor (block 99 for chain2), which reth accepts. However, cross-safe/finalized cannot advance because interop cold start is gated on every dependency-set chain, and one chain (`420120102`) is stuck in a long consensus-layer `FindL2Heads` startup walkback.
    - **Proposed Mitigation**: A supernode-only DB reset/restart with per-chain sync mode set to `execution-layer` is suggested to avoid the large CL startup walkback.
    - **Root Cause Analysis**: Wwared provided a detailed analysis, confirming that the reth engine wedged between `CanonicalBlockAdded` and `CanonicalChainCommitted` for block 47725. The `op-node` also advanced `localSafeHead` then attempted FCU, but a timeout resulted in a `TemporaryError` instead of an engine reset. This creates a scenario where `op-node` believes a block is safe, but `op-reth` cannot provide it.
    - **Conclusion**: There are two distinct bugs amplifying each other: an `op-node` issue with FCU timeout handling and an `op-reth` engine wedging issue, possibly due to ExEx backpressure.
