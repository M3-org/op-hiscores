## NEW ISSUES

### Breaking Change in StorageKeys Value
A new issue [#780] was opened reporting a breaking change in the `StorageKeys` value, specifically that it returns `null` instead of `[]` in `v1.101701.0`. Initial investigation points to `SortedFunc` in `access_list_tracer.go` as the problematic code, where empty arrays are returned as `nil` according to Go Docs.

## ACTIVE ISSUES

### Flaky Test: `TestPreinteropFaultProofs_TraceExtensionActivation`
A new flaky test issue [#19760] was reported for `TestPreinteropFaultProofs_TraceExtensionActivation`. The error indicates an unexpected error during execution. A comment suggests that a pending pull request (ethereum-optimism/optimism#19745) should fix this issue by simplifying the migration process and avoiding ownership reassignment, thereby eliminating a nonce race condition that caused the flake.

### Document Interop Tx Pool Eviction Behavior on Reorg
Discussion continues on documenting the interop transaction pool eviction behavior on reorgs [#19351]. A question was raised regarding what happens to interop transactions already in the mempool during a reorg, and whether they are explicitly dropped or handled by periodic re-evaluation.

### Investigate Adding an Array of Predeploys to Increase Upgrade Safety
An in-depth analysis of the `L2CM` upgrade pipeline revealed a structural gap where there is no centralized source of truth for which implementations need to be deployed, and no automated test validates completeness across multiple data structures [#19260]. While a specific bug related to `L2DevFeatureFlags` was fixed, the underlying architectural issue remains. The analysis highlights a latent `ConditionalDeployer` issue that could lead to a critical failure during future upgrades if not addressed.

### Remove Karst-specific Upgrade Transactions from GenerateNUTBundle
The issue of removing Karst-specific upgrade transactions from `GenerateNUTBundle` [#19369] received a new comment outlining the necessary updates to `UpgradeUtils.getTransactionCount()` and the `GasLimits` struct when these transactions are removed. This ensures consistency and accuracy after the Karst upgrade is fully deployed.

### Prove Withdrawals Using Chain-Specific Root Claim
A question was raised regarding the closure of this issue [#18517], as the approach for proving withdrawals using `IDisputeGame.rootClaim(uint256)` might have changed. The commenter inquired if the switch to `rootClaimByChainId` based on game type has been merged.
