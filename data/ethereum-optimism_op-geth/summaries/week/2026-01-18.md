# ethereum-optimism/op-geth Weekly Report (Jan 18 - 24, 2026)

## 🚀 Highlights
This week, development focused on maintaining parity with upstream Ethereum improvements while refining the stability of the OP Stack's execution layer. Key activities included a series of version updates to integrate the latest `go-ethereum` releases and the resolution of intermittent test failures within the miner component. Significant architectural discussions also took place regarding reset handling for the `op-supernode`, balancing immediate workarounds for Engine API behavior with long-term protocol sustainability.

## 🛠️ Key Developments

### Upstream Integration & Maintenance
The team prioritized keeping the codebase synchronized with the latest upstream developments from the Ethereum mainnet client.
*   **Go-Ethereum Updates**: Successfully merged updates for `go-ethereum` versions v1.16.6, v1.16.7, and v1.16.8. These updates ensure that `op-geth` benefits from the latest security fixes, performance improvements, and features from the core Ethereum ecosystem ([#728](https://github.com/ethereum-optimism/op-geth/pull/728), [#727](https://github.com/ethereum-optimism/op-geth/pull/727), [#751](https://github.com/ethereum-optimism/op-geth/pull/751)).

### Stability and Bug Fixes
Efforts were made to harden the CI/CD pipeline and correct calculation logic within the execution engine.
*   **Flaky Test Mitigation**: Resolved intermittent failures in the miner component, specifically targeting `TestDAFilters` and `TestInteropTxRejectedWithFailsafe`. These fixes improve the reliability of the test suite and reduce "noise" during the development process ([#753](https://github.com/ethereum-optimism/op-geth/pull/753), [#752](https://github.com/ethereum-optimism/op-geth/pull/752)).
*   **Gas Calculation**: A new fix was introduced to address a bug in the calculation of mgas per block, ensuring accurate resource accounting ([#755](https://github.com/ethereum-optimism/op-geth/pull/755)).

### Feature Proposals
*   **RocksDB Support**: A new pull request was opened to introduce RocksDB as an optional database backend, providing contributors and node operators with more flexibility in storage management ([#754](https://github.com/ethereum-optimism/op-geth/pull/754)).

## 🐛 Issues & Triage

### Active Issues & Technical Debt
*   **Supernode Reset Handling**: A major point of discussion remains how `op-supernode` handles derivation and verification resets ([#18740](https://github.com/ethereum-optimism/op-geth/issues/18740)). The team is currently leaning toward a temporary workaround involving synthetic blocks to manage `engine_forkchoiceUpdatedV1` behavior, while evaluating more robust long-term solutions like new Engine API methods.
*   **Batcher Throttling**: Discussions are ongoing regarding implementing throttling mechanisms in `op-reth` to match `op-geth`'s `miner_setMaxDASize` capabilities, ensuring consistent behavior across different execution clients within the Superchain ([#18764](https://github.com/ethereum-optimism/op-geth/issues/18764)).
*   **P2P Connectivity**: Work continues on resolving flakiness in connections between `op-reth` and `op-geth` nodes in system tests, with a fix currently under review ([#18570](https://github.com/ethereum-optimism/op-geth/issues/18570)).
*   **Tooling Migration**: Context was added to the effort of converting `DeploySuperchain` functionality to use Forge, identifying original implementation details to assist in the transition ([#17215](https://github.com/ethereum-optimism/op-geth/issues/17215)).

## 💬 Community & Collaboration
The week's activity highlights a strong collaborative effort between developers working on different client implementations (`op-geth` and `op-reth`). This is evidenced by the cross-client discussions on batcher throttling and P2P stability. The technical dialogue around the Engine API and `op-supernode` resets demonstrates a high level of coordination required to maintain interoperability within the Superchain ecosystem. Contributors are actively engaged in balancing rapid fixes with the long-term architectural integrity of the OP Stack.
