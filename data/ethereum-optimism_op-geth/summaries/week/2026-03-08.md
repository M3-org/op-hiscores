# ethereum-optimism/op-geth Weekly Report (Mar 8 - 14, 2026)

## 🚀 Highlights
This week was defined by a major upstream synchronization with the merge of `go-ethereum v1.17.1`, significantly updating core syncing and block-building packages. The team also made strides in protocol stability by resolving critical derivation pipeline vulnerabilities and addressing configuration discrepancies. While core infrastructure improved, the project is currently navigating challenges related to repository maintenance, specifically regarding large `.git` directory sizes and a newly identified critical crash loop in `op-node` affecting the SuperAuthority path.

## 🛠️ Key Developments

### Core Client & Upstream Synchronization
The primary technical milestone this week was the integration of the latest upstream changes to maintain parity with the Ethereum execution layer.
*   **Go-Ethereum Integration:** Successfully merged `go-ethereum v1.17.1` ([#774](https://github.com/ethereum-optimism/op-geth/pull/774)). This update specifically targets improvements in the syncing and block-building packages, ensuring the OP Stack remains performant and compatible with the latest Geth standards.

### Protocol Robustness & Configuration
Efforts were focused on ensuring the derivation pipeline can handle malformed data without compromising network uptime.
*   **Derivation Pipeline Audit:** Completed a comprehensive audit of external-input error handling ([#19491](https://github.com/ethereum-optimism/op-geth/issues/19491)). This ensures that malformed L1 inputs do not halt the derivation process.
*   **Batch Processing Refinement:** Addressed an issue in the `BatchQueue` where span batch extraction failures were incorrectly triggering critical errors. The team opted to preserve historical behavior for pre-Holocene networks to maintain backward compatibility ([#19511](https://github.com/ethereum-optimism/op-geth/issues/19511)).
*   **Configuration Accuracy:** A fix was initiated via PR #2000 to correct the description of the `max-blocks-per-span-batch` variable, which previously contained mismatched documentation ([#1933](https://github.com/ethereum-optimism/op-geth/issues/1933)).

## 🐛 Issues & Triage

### Closed Issues
*   **Documentation Infrastructure:** The long-standing task of hosting Rust documentation was closed as it has been subsumed into a larger, more comprehensive documentation migration project ([#1985](https://github.com/ethereum-optimism/op-geth/issues/1985)).
*   **Error Handling:** Resolved issues surrounding critical error triggers in the derivation pipeline to prevent unnecessary node halts.

### New & Active Issues
*   **Critical `op-node` Crash Loop:** A high-priority issue ([#19509](https://github.com/ethereum-optimism/op-geth/issues/19509)) was identified where `DepositsOnlyPayloadAttributesRequestEvent` failures lead to a permanent crash loop. This is particularly relevant to the SuperAuthority deny path, and developers are currently evaluating test coverage and potential fixes.
*   **Repository Bloat:** Community members have raised concerns regarding the `optimism` repository's size, which has reached 1.04 GB for the `.git` directory alone ([#19241](https://github.com/ethereum-optimism/op-geth/issues/19241)). This is causing significant friction for new contributors due to multi-hour cloning times.
*   **Memory Leak Investigation:** Discussions continue regarding a database read transaction memory leak in `op-reth` ([#19212](https://github.com/ethereum-optimism/op-geth/issues/19212)). Reports from World Chain users suggest the issue persists in v1.10.1, though v1.10.2 may offer more stability.

## 💬 Community & Collaboration
The week saw active technical discourse between maintainers and the broader ecosystem. Notable interactions included `ajsutton` and other contributors debating the scope of automated tests for the `op-node` crash loop, referencing AI-assisted contributions for test generation. There is also a clear signal from the community (via `incompleteloop`) requesting higher prioritization for "developer experience" issues, specifically regarding repository maintenance and the organization of Rust crates within the monorepo. Collaboration remains high as the team balances rapid protocol evolution with the practicalities of open-source contribution.
