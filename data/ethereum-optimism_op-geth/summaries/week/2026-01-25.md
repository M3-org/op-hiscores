# ethereum-optimism/op-geth Weekly Report (Jan 25 - 31, 2026)

## 🚀 Highlights
This week, development focused on refining protocol parameters and advancing experimental features like flashblocks and sequencer-defined metering. A significant effort was directed toward hardening the system against edge cases, specifically addressing potential vulnerabilities in EIP-1559 parameter decoding. While the team concluded acceptance testing for the Glamsterdam devnet, identifying critical infrastructure challenges, work also progressed on defining the `op-supernode` SyncStatus API to improve cross-chain visibility. The week was characterized by a transition from theoretical design to initial Proof of Concept (PoC) implementations for core protocol upgrades.

## 🛠️ Key Developments
While much of the week was dedicated to design discussions and issue triage, concrete progress was made in the following areas:

### Protocol Metering & Gas Experiments
The project is moving toward more granular control over network resources. A new Proof of Concept (PoC) for **opgas** was introduced in [#758](https://github.com/ethereum-optimism/op-geth/pull/758). Additionally, the scope for the **Sequencer-Defined Metering** design document was expanded to include a PoC to unblock the design phase, with benchmarking planned following the January 30 devnet deployment [#360](https://github.com/ethereum-optimism/op-geth/issues/360).

### Infrastructure & Tooling Updates
- **Gas Configuration Documentation:** A new guide was finalized detailing how to modify gas configuration values on the system config post-Holocene [#1944](https://github.com/ethereum-optimism/op-geth/issues/1944).
- **Cleanup:** Obsolete code related to OPCM v2 checks was removed to enable CGT, and resource locators for v7_0_0 artifacts were updated [#18536](https://github.com/ethereum-optimism/op-geth/issues/18536), [#18633](https://github.com/ethereum-optimism/op-geth/issues/18633).

## 🐛 Issues & Triage

### Closed Issues
- **Acceptance Testing:** The dry run for acceptance tests against the first Glamsterdam devnet (bal-devnet-1) was concluded. The process highlighted several friction points, including custom L1 setup complexities and inconsistent RPC responses [#18755](https://github.com/ethereum-optimism/op-geth/issues/18755).

### New & Active Issues
- **Critical Vulnerability Research:** A potential division-by-zero panic was identified in `CalcBaseFee`. This occurs when an `elasticity == 0` value is decoded from Optimism `extraData`, prompting a need for more robust parameter handling in `op-alloy` [#757](https://github.com/ethereum-optimism/op-geth/issues/757), [#18951](https://github.com/ethereum-optimism/op-geth/issues/18951).
- **Flashblocks Support:** Discussions began regarding adding Geth support for flashblocks, specifically focusing on processing WebSocket events and reconstructing payloads for live tracing [#756](https://github.com/ethereum-optimism/op-geth/issues/756).
- **Sync & Configuration Management:** 
    - The `op-batcher` sync logic is under review, with a proposal to treat outdated rollup configurations as critical errors to force a process restart and reload [#18178](https://github.com/ethereum-optimism/op-geth/issues/18178).
    - The `op-supernode` SyncStatus API is being defined to include per-chain sync status and interop-specific verification timestamps [#18947](https://github.com/ethereum-optimism/op-geth/issues/18947).
- **Post-Fusaka Compatibility:** Users reported "transaction gas limit too high" errors in `op-deployer` following the Fusaka hardfork, suggesting a need for transaction optimization or breakdown to meet new network caps [#17912](https://github.com/ethereum-optimism/op-geth/issues/17912).

## 💬 Community & Collaboration
The week saw active engagement from the community, particularly regarding the EIP-1559 parameter decoding fix, where community members stepped forward to take on implementation tasks. Collaboration between maintainers and users was also evident in the troubleshooting of `op-deployer` versions for alt-da users. Technical discussions remain high-density, particularly around the architectural requirements for the Superchain's interoperability layers and the transition to OPCM v2 across the broader stack.
