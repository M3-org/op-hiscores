# ethereum-optimism/op-geth Weekly Report (Jun 7 - 13, 2026)

## 🚀 Highlights
This week, development focused on protocol standardization and architectural refinement within the OP Stack. A primary objective was the formal renaming of the "Interop" hardfork to "Lagoon" to ensure naming consistency across all components. Simultaneously, significant progress was made in auditing and planning the centralization of L1/L2 hardfork mappings within the Rust stack to eliminate redundancy and prevent latent bugs. These efforts reinforce the project's commitment to protocol security and maintainability as the Superchain ecosystem evolves.

## 🛠️ Key Developments

### Protocol Standardization & Hardfork Naming
To improve clarity and consistency across the OP Stack, the team initiated a transition in naming conventions for upcoming protocol upgrades.
*   **Lagoon Hardfork Renaming:** A new pull request was opened to rename the "Interop" hardfork to "Lagoon" across all relevant codebase components. This change ensures that all developers and tools use a unified nomenclature for this milestone. [#803](https://github.com/ethereum-optimism/op-geth/pull/803)

### Rust Stack Architectural Refinement
Significant effort was directed toward resolving technical debt related to how L2 (Optimism) hardforks map to their corresponding L1 (Ethereum) counterparts.
*   **Fork Mapping Centralization:** An in-depth analysis revealed that L1/L2 fork mappings were duplicated in seven distinct locations within the Rust stack. This fragmentation led to a latent bug where the `Karst → Osaka` mapping was missing in certain areas. 
*   **Implementation Plan:** A comprehensive strategy was drafted to centralize these mappings into `alloy-op-hardforks`. The plan involves creating a single canonical table, deriving views for consumers, and removing OP-fork specific knowledge from `kona-engine` to improve modularity and prevent future inconsistencies. [#21338](https://github.com/ethereum-optimism/op-geth/issues/21338)

## 🐛 Issues & Triage

### New & Active Issues
*   **Optimizing Withdrawal Timelines:** Discussions continued regarding the adjustment of `MAX_CLOCK_DURATION` and air gap constants. This work is critical for enabling faster withdrawals via ZK proofs. Technical debate centered on the history requirements for proofs; while theoretically unbounded, the practical limit is tied to proposal frequency. Notably, it was clarified that the withdrawal root in the Isthmus upgrade allows for the reconstruction of output roots without requiring extensive historical data during challenges. [#20774](https://github.com/ethereum-optimism/op-geth/issues/20774)
*   **Mapping Consistency:** The discovery of the missing `Karst → Osaka` mapping has elevated the priority of the Rust stack refactor. The proposed solution includes adding consistency tests for `op-revm` to ensure no new dependencies are introduced while maintaining accuracy across the stack. [#21338](https://github.com/ethereum-optimism/op-geth/issues/21338)

## 💬 Community & Collaboration
The week's activity highlights a high level of coordination between protocol engineers regarding the long-term maintainability of the OP Stack. The detailed analysis of the Rust stack mappings suggests a collaborative effort to identify and fix systemic technical debt before it impacts production stability. Furthermore, the ongoing dialogue surrounding ZK proof constants demonstrates active engagement between contributors to balance security with the user experience of faster withdrawals.
