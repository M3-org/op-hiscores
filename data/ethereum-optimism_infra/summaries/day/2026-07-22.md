## ACTIVE ISSUES

### VM-Runner ZK Execution Support
Discussion on [#18325](https://github.com/ethereum-optimism/infra/issues/18325) continues regarding the integration of ZK execution into `vm-runner`. The latest comment provides benchmark results for running the super-range program in mock proving mode, showing that while memory usage is high (around 13GiB), it's feasible to continuously check the latest L2 head using the mock prover. Previous discussions highlighted the need for Rust for actual ZK execution due to `sp1` dependency and the possibility of embedding a Rust executor.

### Flaky Test: `TestSupernodeInteropChainLag`
Issue [#19610](https://github.com/ethereum-optimism/infra/issues/19610) saw a recurrence of the `TestSupernodeInteropChainLag` flake today in the `memory-all-opn-op-reth` job. The test previously had a fix implemented ([#19614](https://github.com/ethereum-optimism/optimism/pull/19614)) that added `Eventually` waits for preconditions, but its reappearance suggests further investigation may be needed.

### Flaky Test: `TestNotTruncateDatabaseOnRestartWithExistingDatabase`
A new occurrence of the flake in `TestNotTruncateDatabaseOnRestartWithExistingDatabase` was reported on [#20649](https://github.com/ethereum-optimism/infra/issues/20649). The failure points to a "pre-restart baseline-race" where the baseline is sampled from the live safe head while the safe head DB resolves per L1 origin. A fresh PR ([#21975](https://github.com/ethereum-optimism/optimism/pull/21975)) has been opened to re-land a fix for this, as a previous attempt was auto-closed.

### Flaky Test: `TestSupernodeInterop_SafeHeadProgression`
Issue [#20851](https://github.com/ethereum-optimism/infra/issues/20851) reported another occurrence of the `TestSupernodeInterop_SafeHeadProgression` flake. The error "expected head to advance: safe" was encountered in the `memory-all-kona-op-reth` job. A fix PR ([#20852](https://github.com/ethereum-optimism/optimism/pull/20852)) was previously opened for this issue.

### Flaky Test: `TestSingleChainSuperFaultProofsFromOpNode`
Issue [#21952](https://github.com/ethereum-optimism/infra/issues/21952) was closed today after a root cause was identified and a fix implemented in ethereum-optimism/optimism#21937. The flake was caused by `sysgo.getSuperRoot` encountering a 10s RPC deadline timeout under CI load, leading to a transient failure. The fix refactored the function to reuse polled responses and remove a redundant RPC call.

### Light-Sequencer Oscillation During Recovery
A new occurrence was logged for [#21964](https://github.com/ethereum-optimism/infra/issues/21964), upgrading the issue from a convergence-time problem to a correctness problem. The oscillation in the light-sequencer configuration can lead to the sync-start recovery path relabeling a local fork as safe/finalized, even if it's on the wrong chain. This was observed in `TestSupernodeLightSequencerInteropInvalidMessageReplacement`, where a transaction was missing from a block that was incorrectly marked as safe.
