# ethereum-optimism/infra Daily Update (Aug 21, 2026)
## OVERVIEW 
The day saw significant progress in Lokahi's multi-chain interop node development, with key components like the verification round loop, persistent stores, and sequencer mode being implemented. Efforts also focused on abstracting the devstack's supernode test control and addressing a flaky test.

## KEY TECHNICAL DEVELOPMENTS

### Lokahi Multi-Chain Interop Node Advancements
Lokahi's core multi-chain interop node functionality has been significantly expanded. The verification round loop is now implemented, enabling the node to observe chains, make decisions, log them, and apply them. This includes handling cold starts and backfilling log stores. Additionally, the persistent stores for verified data, logs, and invalidated outputs have been integrated, providing robust data management for the interop actor. The sequencer mode has also been enabled, allowing Lokahi to configure and run Kona's `SequencerActor` per chain.
- Verification Round Loop: [#22536](https://github.com/ethereum-optimism/infra/issues/22536)
- Persistent Stores: [#22535](https://github.com/ethereum-optimism/infra/issues/22535)
- Sequencer Mode: [#22545](https://github.com/ethereum-optimism/infra/issues/22545)

### Devstack Supernode Test Control Abstraction
The `stack.SupernodeTestControl` in the devstack has been refactored to be RPC-shaped, moving away from in-process object handling. This change makes the test control implementable out of process, which is crucial for integrating Lokahi into the acceptance matrix.
- Abstraction of SupernodeTestControl: [#22546](https://github.com/ethereum-optimism/infra/issues/22546), [#22547](https://github.com/ethereum-optimism/infra/issues/22547)

### Lokahi RPC and Interop Activation
Lokahi's RPC now includes `supernode_syncStatus` and `superroot_atTimestamp` endpoints, designed to be wire-compatible with existing Go schemas. This enables crucial communication with components like `op-proposer` and `op-challenger`. Discussions around interop activation confirmed that for the initial release, activation time and Lagoon hard fork activation will be at the same timestamp, with a testing override deferred for later.
- Supernode RPCs: [#22544](https://github.com/ethereum-optimism/infra/issues/22544)
- Interop Activation: [#22536](https://github.com/ethereum-optimism/infra/issues/22536)

### Kona Node Service Refactoring and Lokahi Scaffolding
The `kona-node-service` has been refactored to provide a shared single-chain composition entry point, ensuring consistency between `kona-node` and `lokahi` wirings. This is a foundational step for Lokahi's N-chain scaffolding. The multi-chain L1 watcher has also been completed, and the `lokahi` N-chain service composition and configuration have been landed, allowing `lokahi node --config <file>` to run N chains in one process.
- Shared Single-Chain Composition: [#22530](https://github.com/ethereum-optimism/infra/issues/22530)
- N-Chain Scaffolding and Composition: [#22521](https://github.com/ethereum-optimism/infra/issues/22521), [#22532](https://github.com/ethereum-optimism/infra/issues/22532)

## NEW ISSUES
### Flaky Test Identification
A timing-dependent acceptance test, `TestSDMActivatesAtLagoonBoundary`, has been identified as flaky. The root cause has been confirmed as the sequencer starting during setup and catching synthetic L2 time up to wall clock before the test's initial pre-Lagoon assertion. A fix has been proposed to start the sequencer paused and queue transactions deterministically.
- Flaky Test: [#22630](https://github.com/ethereum-optimism/infra/issues/22630)

### Observations from Lokahi Mirroring op-supernode
During the development of Lokahi, several observations were made regarding `op-supernode`'s behavior that may not be intentional. These include `kona-node` lacking `op-node`'s `opstack` block-building namespace and `kona-node` having no `superroot` namespace, unlike `op-node`. These discrepancies could lead to `Method not found` errors in certain devstack configurations.
- op-supernode Observations: [#22636](https://github.com/ethereum-optimism/infra/issues/22636)

## ACTIVE ISSUES
### Kona Node Service: EngineActor becomes ChainController [#22527](https://github.com/ethereum-optimism/infra/issues/22527)
The discussion on renaming `EngineActor` to `ChainController` and extending its functionality has progressed. A key point of discussion was the read-only query handler, which was found to be already available and made meaningful by a previous PR. The atomicity of the L2 block and L1 key pairing was clarified, emphasizing that it relies on the pairing living in the state plus a single borrow. The Go side's `OptimisticAt` function was noted to still have a structural gap in atomicity despite its intended fix. The four possible verdicts for a timestamp query were detailed, highlighting the importance of distinguishing between them to avoid incorrect behavior in consumers. An incidental fix was made to `engine.mdx` regarding `InsertTask` snippets. The implementation of the bulk of this issue was opened as PR #22595, stacked on #22586. It was noted that mediating derivation-bound signals and owning reset initiation, along with depth-1 lockstep confirmation, were already handled by earlier slices. The `descends-from-local-safe` check was determined not to belong in the controller due to potential race conditions and task queue behavior. The query handler was deferred, with the obstacle being where the L2→L1 pairing is recorded. After a correction, it was concluded that the write hook for the pairing belongs in `kona-engine`'s sync state, not the `ChainController`, to ensure correctness and avoid dependency cycles.

### Lokahi: N-chain scaffolding without interop (phase 2) [#22521](https://github.com/ethereum-optimism/infra/issues/22521)
The status of Phase 2 items was reviewed. The multi-chain L1 watcher (#22531) is done. The shared single-chain composition entry point (#22530) is startable and now open as #22598. The `lokahi` N-chain composition and config (#22532) requires merging multiple branches, making it the first item to demonstrate N>1 chains. The `sysgo` component and 2-chain smoke test (#22533) depend on #22532. It was noted that nothing in this phase demonstrates N>1 until #22532. A previous decision by @ajsutton confirmed that the L1 watcher's fixed, non-empty chain set stands, meaning chains cannot be dynamically added to a running `lokahi` instance. This simplifies the design by ensuring that config validation rejects an empty chain list before the watcher is constructed.

### Kona-node-service: shared single-chain composition entry point [#22530](https://github.com/ethereum-optimism/infra/issues/22530)
Notes from the implementation of this issue were provided. The key insight was that the seam is between composition and running, not just extracting a function. Splitting `RollupNode::start` into `compose` and `run_actors` makes it reusable for multi-chain hosts. The `spawn_and_wait!` macro was replaced with `ErasedNodeActor` to handle actors of unrelated types. The L1 watcher was deliberately kept separate from a chain's composition, returning `L1WatcherPorts` for the host to decide how many watchers to attach. `RollupNode` remains the per-chain unit to avoid duplicating configuration fields. Spawn order changed but is not expected to matter. A sequencing note for #22532 highlighted the need to reconcile different branches. A visible gap is that a dying actor cannot say which chain it belonged to, which will become more apparent with N chains. The "two wirings cannot drift" property is currently structural and not yet demonstrated by a second consumer.

### Lokahi: N-chain service composition and config [#22532](https://github.com/ethereum-optimism/infra/issues/22532)
The implementation of this issue was landed as #22599, allowing `lokahi node --config <file>` to run N chains in one process. This involved merging #22567 and #22569 into the composition line of #22598. Several points of disagreement during the merge were resolved, including the L1 head watch, where a watcher is attached, and the engine's chain ID. A latent test bug was exposed and fixed. The `NodeActor::Error` now includes chain labels for better debugging in multi-chain environments. A hand-off for #22533 noted that the CI job for release binaries will need to include `lokahi`.

### Lokahi: cross-safe promotion lifecycle and finality [#22537](https://github.com/ethereum-optimism/infra/issues/22537)
The implementation of this issue is in PR #22610. The main challenge was wiring the interop actor as the promotion source, as `lokahi` did not previously depend on `lokahi-interop`. Promotions now route through Kona's existing external promoter entry point, ensuring that the interop actor is the sole cross-safe writer for a chain. `kona-safedb` gained a writer, recording paired local-safe advances and rewinding across resets. Interop activation is now all-or-nothing across the hosted set. A decision was deliberately left to the team regarding clamping internal actor writes below finalized. The suspected finality gap was found not to exist, as `finalize/task.rs` already drops finality signals for blocks not yet cross-safe.
