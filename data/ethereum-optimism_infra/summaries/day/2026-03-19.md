### Initial EL Sync UX and Correctness
Discussion continued on the `op-node`'s initial EL Sync behavior, specifically regarding the setting of safe and finalized heads. The current implementation is deemed incorrect as it sets safe/finalized heads equal to the unsafe head after initial sync, rather than respecting the L1 finalization gadget.
- **Correctness vs. UX:** The core problem involves balancing correctness (ensuring safe/finalized reflect L1) with user experience (reducing sync time).
- **Proposed Solutions:**
    - Setting safe/finalized to genesis (simplest, but slow).
    - Setting safe/finalized to unsafe head minus sequencer window (improves UX while maintaining correctness, requiring ~12 hours of derivation).
    - Allowing external sources for safe/finalized heads (best UX, but adds complexity and trust assumptions).
- **Current Consensus:** Option 2 (sequencer window delay) is seen as a reasonable balance, though the node will still need time to derive forward.
- **Related Observations:** An edge case in `insertUnsafePayload` was noted where `newPayload` returning `SYNCING` followed by `forkchoiceupdated` returning `VALID` could miss the `syncStatusFinishedELButNotFinalized` state transition, affecting safe/finalized head updates. [#17631](https://github.com/ethereum-optimism/infra/issues/17631)

### Non-Terminating CI Job: memory-all-opn-op-geth
This issue, tracking a non-terminating CI job, saw significant activity today, including a root cause analysis and a proposed fix.
- **Root Cause Identified:** A mutex deadlock in `VirtualNode` during shutdown was pinpointed. This deadlock involves the test cleanup thread, `Start()` goroutines holding `v.mu` while calling `OpNode.Stop()`, and event loop goroutines trying to acquire `v.mu` via `SyncStatus()`.
- **Flakiness Explanation:** The deadlock is timing-dependent, occurring only when specific event processing coincides with `Start()` acquiring the mutex during shutdown.
- **Proposed Fix:** A fix PR has been created in the `optimism` repository to release `v.mu` before calling `inner.Stop()` and add a defensive timeout to `Supernode.Stop()`.
- **Recent Occurrences:** The job continued to hang, specifically on `TestChallengerRespondsToMultipleInvalidClaimsEOA`, reinforcing the need for the identified fix. [#19563](https://github.com/ethereum-optimism/infra/issues/19563)
