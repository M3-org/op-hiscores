## CLOSED ISSUES

*   **Go-side Cross-Unsafe Head Removal**
    *   The issue tracking the removal of the cross-unsafe chain-head notion from Go components (op-node, op-service, op-devstack) was closed today. This change aligns the Go codebase with the current interop design where a distinct cross-unsafe head is no longer produced, addressing a vestige from the op-supervisor era. The message-level cross-unsafe validation in the tx-pool admission path remains untouched as it is live functionality ([#22550](https://github.com/ethereum-optimism/infra/issues/22550)).

## ACTIVE ISSUES

*   **Kona Engine: Targeted Reset Functionality** ([#22526](https://github.com/ethereum-optimism/infra/issues/22526))
    *   Discussion centered on the implementation of a `reset_to` variant for the Kona engine, allowing explicit target heads and skipping RPC-walkback for start-point discovery. A key point was ensuring that resets never move the cross-safe head forward, and how `op-node` handles this automatically versus Kona's explicit maintenance. The design decision to place the cross-safe head clamp in the state transition (`apply_update`) rather than `reset_to` was highlighted. The difference in retry ceilings between `reset` (unbounded) and `reset_to` (bounded) was also noted.

*   **Kona Engine: Local/Cross-Safe Vocabulary and Promotion Entry Point** ([#22525](https://github.com/ethereum-optimism/infra/issues/22525))
    *   The discussion focused on renaming head vocabulary to explicitly distinguish local-safe and cross-safe, and enforcing a single promotion entry point for cross-safe. Key insights included the structural seal of `cross_safe_head` within the `kona-engine` crate, and how two heads (derivation actor and consolidation) had to be re-pointed in opposite directions to maintain correctness. A pre-existing `cargo test` vs `cargo nextest` disagreement for this crate was also noted.

*   **Kona: `chain_id` Metric Label** ([#22529](https://github.com/ethereum-optimism/infra/issues/22529))
    *   The conversation revolved around adding a `chain_id` label to Kona's existing metrics. Challenges included the macro surface not supporting variadic labels, leading to a change in argument order for `set!`/`record!` macros. The state of unit tests for metrics was also discussed, as they were found to be failing due to global recorder installation. The scope of the implementation was limited to `kona-engine` with a note that a full sweep across all crates would be a larger effort.

*   **Lokahi: Interop Actor, Cross-Safe Happy Path (Phase 3)** ([#22522](https://github.com/ethereum-optimism/infra/issues/22522))
    *   The discussion involved decisions from a Slack design discussion regarding retention and storage engine for Lokahi, the WAL-replay hazard for the invalidated-output archive, and the divergence in activation sources between Kona and op-supernode.

*   **Lokahi: Multi-Chain L1 Watcher** ([#22531](https://github.com/ethereum-optimism/infra/issues/22531))
    *   Notes from implementing the multi-chain L1 watcher highlighted how `tokio::select!` shaped the refactor due to borrowing conflicts when handling per-chain state. The decision to keep one `eth_getLogs` call per chain per L1 head was deliberate to maintain wire-identity for standalone Kona nodes. The fixed, non-empty chain set at construction was also discussed, with the implication that an empty set would cause a panic.

*   **Lokahi: N-Chain Service Composition and Config** ([#22532](https://github.com/ethereum-optimism/infra/issues/22532))
    *   A key decision from Adrian Sutton was confirmed: the L1 watcher's fixed, non-empty chain set is correct by design, as chains cannot be dynamically attached to a running instance, and a zero-chain configuration is invalid. This clarifies that the issue does not need to relax the assert or introduce a dynamic-attachment API.

*   **Kona-Interop: Consolidate Shared Message-Validity Rules** ([#22534](https://github.com/ethereum-optimism/infra/issues/22534))
    *   Discussions focused on consolidating interop message-validity rules into `kona-interop`. A significant point was the absence of a Rust counterpart for the type-3 access-list checksum computation, which is crucial for `lokahi`'s verifier parity with `op-supernode`. It was later clarified that the checksum is an implementation detail for the log store, not a consensus protocol check, and belongs in `lokahi`'s interop store work. The decision was made to implement the shared interop rules as methods on a `MessageRules` type rather than standalone functions for better organization.

*   **Lokahi-Interop: Stores (verifiedDB + WAL, logsDBs, invalidated-output archive)** ([#22535](https://github.com/ethereum-optimism/infra/issues/22535))
    *   A key decision from Adrian Sutton was to use RocksDB for stores and to start with no pruning, adding it later if needed. It was clarified that `op-supernode` moved to a raft-wal implementation, and the custom logsdb backend is not desired. Analysis of "O(1) `Contains`" revealed it's two separate properties, and sizing estimates showed logsDB dominating storage. The invalidated-output archive was identified as the only store whose loss is unrecoverable and fault-proof-visible, requiring its own database and backup strategy.

*   **Lokahi-Interop: Verification Round Loop** ([#22536](https://github.com/ethereum-optimism/infra/issues/22536))
    *   The decision was made to defer the activation-timestamp override for the initial release, keeping it as a potential follow-up. It was confirmed that Kona's per-chain fork check and Supernode's cluster-wide check compute the same thing currently due to startup invariants. The discussion also highlighted where future depset activation would land in the code.

*   **Lokahi-Interop: Invalidate Decision Path** ([#22540](https://github.com/ethereum-optimism/infra/issues/22540))
    *   The primary hazard discussed was ensuring the archive write is driven by the interop actor from the WAL, independently of which branch replay takes, to prevent data loss during crash-replay. It was noted that the archive cannot borrow the deny list's fail-open handling, and that no cross-store atomicity with the replacement is required. The importance of specific intra-function ordering for `denyList.Add` was also highlighted.

*   **Lokahi: `supernode_syncStatus` and `superroot_atTimestamp` RPCs** ([#22544](https://github.com/ethereum-optimism/infra/issues/22544))
    *   Adrian Sutton's decision that superroots must be answerable over the full fault-dispute window, with an option for unbounded retention, was discussed. This implies that the invalidated-output archive needs a robust durability and backup story, as a missing entry would return an incorrect superroot without error.
