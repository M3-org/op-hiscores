## ACTIVE ISSUES

### Kona Engine: Targeted Reset Functionality
Discussion on [#22526](https://github.com/ethereum-optimism/infra/issues/22526) confirms the implementation of a targeted reset variant (`reset_to`) that allows explicit target heads and skips RPC-walkback start-point discovery. A key insight from the implementation is that "resets never move cross-safe" means never moving it *forward*; rewinding is self-correcting in `op-node` due to its read-time recomputation of the cross-safe head. In `kona`, where `cross_safe_head` is stored, the invariant must be maintained explicitly, with the bound belonging in the state transition (`apply_update`) rather than the reset itself. The `reset_to` function deliberately contains no clamp of its own, and its test asserts the ordering end-to-end. A deliberate difference between `reset` and `reset_to` is the retry ceiling: `reset` retries forever as each retry can yield new information, while `reset_to` has a small bounded number of retries as its heads are fixed by the caller.

### Kona Engine: Local/Cross-Safe Vocabulary and Single Cross-Safe Promotion Entry Point
Issue [#22525](https://github.com/ethereum-optimism/infra/issues/22525) discusses the renaming of head vocabulary to explicit local-safe/cross-safe and making cross-safe writable only through a single promotion entry point. The discussion highlights that the structural seal for `cross_safe_head` is enforced at the crate boundary, with `CrossSafePromotion::new` being reachable only within `kona-engine`. Two heads had to be re-pointed in opposite directions: the depth-1 lockstep confirmation to the derivation actor must carry *local*-safe, while `FinalizeTask`'s sanity check went to cross-safe. A pre-existing `cargo test` vs `cargo nextest` disagreement on this crate was noted, where `cargo test` shows failures due to `PrometheusBuilder::install_recorder()` setting a process-global recorder.

### Kona: Chain_ID Metric Label
On [#22529](https://github.com/ethereum-optimism/infra/issues/22529), the implementation of adding a `chain_id` label dimension to Kona's existing metric names is discussed. A key challenge was that the existing `set!` and `record!` macros in `metrics.rs` lacked a variadic-label arm, leading to a design decision where new arms take the value *first* to avoid rewriting ~300 existing call sites. The issue also notes that the one unit test asserting a rendered metric string was not passing on the base commit due to `PrometheusBuilder::install_recorder()` setting a process-global recorder, which was addressed by switching to `metrics::with_local_recorder`. The scope of the implementation was limited to `kona-engine` (14 call sites), with the understanding that a full sweep across all 8 crates would be a larger effort.

### Lokahi: N-Chain Service Composition and Config
Discussion on [#22532](https://github.com/ethereum-optimism/infra/issues/22532) details the implementation of N-chain service composition, allowing `lokahi node --config <file>` to run multiple chains in one process. Key points include the L1 head watch now being published per chain, the engine's chain ID running through the promotion path, and a latent test bug exposed by the merge. A decision from @ajsutton confirms that the L1 watcher's fixed, non-empty chain set stands, meaning chains cannot be attached to a running instance, and a zero-chain configuration is not permitted.

### Lokahi: Multi-Chain L1 Watcher
On [#22531](https://github.com/ethereum-optimism/infra/issues/22531), notes from implementing the multi-chain L1 watcher highlight that `tokio::select!` shaped the refactor more than the fan-out itself, as per-chain state in a `Vec` caused collisions. The handlers cannot be `async fn(&self, ..)` on the actor due to `#[async_trait]` boxing `step`'s future as `Send`. One `eth_getLogs` per chain per L1 head is deliberately maintained to preserve standalone Kona-node behavior. Per-chain query channels remain individually fatal, and chain labels are intentionally omitted from watcher log lines for now. The chain set is fixed at construction, and an empty set results in a panic.

### Kona-Interop: Consolidate Shared Message-Validity Rules
Issue [#22534](https://github.com/ethereum-optimism/infra/issues/22534) focuses on making `kona-interop` the single home for interop message-validity rules. A key discussion point was the checksum computation: @ajsutton clarified that it is not a consensus-protocol check but an implementation detail of the log store for space efficiency, belonging in Lokahi's interop store work ([#22535](https://github.com/ethereum-optimism/infra/issues/22535)) rather than shared validity rules. The decision was made for the shared interop rules surface to be a type (`MessageRules`) with methods, rather than free functions, to improve code organization. An enumeration of pre-existing implementations of the five rules (activation invariant, timestamp ordering, 7-day expiry window, checksum existence, same-timestamp cycle check) was provided, noting that checksum existence had no Rust implementation and was not invented.

### Lokahi-Interop: Stores (VerifiedDB + WAL, LogsDBs, Invalidated-Output Archive)
On [#22535](https://github.com/ethereum-optimism/infra/issues/22535), the implementation of the `lokahi-interop` crate with all three stores (verified store, log store, invalidated-output archive) is discussed. Key decisions included using RocksDB for stores, binary encoding for efficiency, and allocating WAL decision tags only for existing transitions. A follow-up note highlights two issues: the archive decode path preallocates from an on-disk count before validating it, and an unrecognised WAL decision tag is reported as data corruption, which might be a downgrade rather than corruption.
