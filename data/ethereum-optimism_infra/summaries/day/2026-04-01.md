# ethereum-optimism/infra Daily Update (Apr 1, 2026)

## OVERVIEW 
Today's development focused on enhancing the `proxyd` service with new features for tracking block hashes and significant refactoring for improved clarity and reusability. Several critical issues were also identified and are being addressed across various Optimism components.

## KEY TECHNICAL DEVELOPMENTS

### `proxyd` Consensus State Enhancements
The `proxyd` service now tracks `safeBlockHash` and `finalizedBlockHash` in its consensus state, improving the accuracy of block hash fetching from the Execution Layer. This change stores block hashes that were previously discarded.
- feat(proxyd): track block hashes in consensus state. ([#591](https://github.com/ethereum-optimism/infra/pull/591))

### `proxyd` Code Refactoring and Clarity
Significant refactoring in `proxyd` involved renaming generic functions to explicitly EL-scoped names for better clarity and extracting a duplicated hash-verification walk-back loop into a reusable function. This also addressed type assertion panics.
- refactor(proxyd): rename EL-specific functions and fix type assertion panics. ([#592](https://github.com/ethereum-optimism/infra/pull/592))
- refactor(proxyd): extract findConsensusBlock walk-back into reusable function. ([#590](https://github.com/ethereum-optimism/infra/pull/590))

## NEW ISSUES

### `op-node` and `op-batcher` Derivation Logic Issues
Several issues were identified in `op-node` and `op-batcher` related to incorrect channel size calculation during frame pruning and comparing the oldest L1 origin against the latest instead of the actual oldest.
- fix(op-batcher): oldest L1 origin compared against latest instead of oldest ([#19859](https://github.com/ethereum-optimism/infra/issues/19859))
- fix(op-node/derive): channel size incorrect when pruning frames after last frame ([#19858](https://github.com/ethereum-optimism/infra/issues/19858))

### `op-service` and `contracts-bedrock` Error Message Inconsistencies
Problems were found in `op-service` where `Bytes256.UnmarshalText` and `Blob.UnmarshalText` reported incorrect type names in error messages. Similarly, `contracts-bedrock` had misleading error messages for `LivenessModule`'s `minOwners` and `SystemConfig`'s base fee checks.
- fix(op-service/eth): Bytes256.UnmarshalText reports wrong type name (Bytes32) ([#19862](https://github.com/ethereum-optimism/infra/issues/19862))
- fix(op-service/eth): Blob.UnmarshalText uses wrong hexutil label (Bytes32) ([#19864](https://github.com/ethereum-optimism/infra/issues/19864))
- fix(contracts-bedrock): LivenessModule minOwners error message contradicts require ([#19866](https://github.com/ethereum-optimism/infra/issues/19866))
- fix(contracts-bedrock): SystemConfig base fee require message contradicts <= check ([#19868](https://github.com/ethereum-optimism/infra/issues/19868))

### `op-node/p2p` and `op-service` Resource Management
Issues were reported regarding `op-node/p2p`'s gossip publisher not closing `blocksV3/blocksV4` topics on shutdown, potentially leading to resource leaks. Additionally, `op-service`'s `EthClient.FetchReceipts` was found to discard an unused `ToBlockID` result, and `CachingReceiptsProvider` could leak fetching locks on errors.
- fix(op-node/p2p): gossip publisher does not close blocksV3/blocksV4 on shutdown ([#19860](https://github.com/ethereum-optimism/infra/issues/19860))
- fix(op-service): EthClient.FetchReceipts discards unused ToBlockID result ([#19870](https://github.com/ethereum-optimism/infra/issues/19870))
- fix(op-service): CachingReceiptsProvider leaks fetching lock on FetchReceipts error ([#19875](https://github.com/ethereum-optimism/infra/issues/19875))

### Kona Protocol Decoding Error
A problem was identified in `kona/protocol` where span batch gas decode errors were incorrectly reported as `TxNonces` instead of a more specific gas-related error.
- fix(kona/protocol): span batch gas decode errors reported as TxNonces ([#19873](https://github.com/ethereum-optimism/infra/issues/19873))

## ACTIVE ISSUES

### Document interop tx pool eviction behavior on reorg ([#19351](https://github.com/ethereum-optimism/infra/issues/19351))
The discussion revolves around the behavior of interop transaction eviction from the transaction pool during reorgs. @karlfloersch clarified that with `op-reth`, all interop transactions are dropped for implementation simplicity and stronger safety guarantees. @pcw109550 raised a question about whether the mempool explicitly iterates and drops existing interop transactions or if periodic re-evaluation handles this. The current approach with `op-geth` drops executing messages, which were intended for reinjection. The team will consider re-evaluating this behavior, especially concerning re-verification of interop transactions before re-adding them to the mempool.
