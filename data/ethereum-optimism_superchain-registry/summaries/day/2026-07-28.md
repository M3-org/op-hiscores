## ACTIVE ISSUES

### Post-Migration OPCM Upgrades
Discussion on [#21731](https://github.com/ethereum-optimism/superchain-registry/issues/21731) revolves around ensuring post-migration `OPContractsManager` (OPCM) upgrades work for all chains in an interop set. The core problem is that member chains can have different `ProxyAdmin` contracts, as long as they share the same L1 ProxyAdmin owner. Two main approaches are being considered:

*   **Option 1: Resolve ProxyAdmin during upgrade:** This approach would have all chains upgrade shared components, with `OPCM.upgrade` being idempotent. While this ensures all chains are upgraded, concerns were raised about potential inconsistencies during the upgrade and the need for careful post-upgrade checks.
*   **Option 2: Skip updating shared components if ProxyAdmin differs:** This would mean only chain 0 in a dependency set upgrades shared contracts. The downside is that if `opcm.upgrade` is called on other chains with a different game config, shared components might not be updated, leading to potential incompatibilities if contracts interact.

The latest comments indicate a leaning towards Option 1, despite the concerns, as it is seen as preferable to the potential for silently unapplied configurations or un-upgraded contracts in Option 2. The discussion also emphasizes the need for shared components to be backward compatible or fail gracefully if upgraded independently.
