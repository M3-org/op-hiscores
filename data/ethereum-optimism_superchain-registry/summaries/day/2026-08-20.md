# ethereum-optimism/superchain-registry Daily Update (Aug 20, 2026)
## OVERVIEW 
Today's development focused on foundational work for the Lokahi interop actor, including refining cross-chain verification rules, multi-chain L1 watcher generalization, and initial store design. A significant Go-side cleanup removed a vestigial cross-unsafe chain-head notion.

## KEY TECHNICAL DEVELOPMENTS

### Lokahi Interop Actor Refinements
Significant progress was made on the Lokahi interop actor, focusing on core verification logic and architectural decisions. This included consolidating shared message-validity rules into a dedicated `MessageRules` type in `kona-interop`, ensuring consistent application across the verifier and proof sides. Discussions clarified that the checksum existence check is an implementation detail for the log store, not a consensus-level rule, and thus belongs in Lokahi's store work rather than shared validity rules. The activation timestamp override for testing was deferred, and the L1 watcher's fixed, non-empty chain set at construction was confirmed as correct by design.
[#22534](https://github.com/ethereum-optimism/superchain-registry/issues/22534), [#22536](https://github.com/ethereum-optimism/superchain-registry/issues/22536), [#22532](https://github.com/ethereum-optimism/superchain-registry/issues/22532)

### Multi-Chain L1 Watcher Generalization
The `L1WatcherActor` was generalized to handle multiple chains, moving from a per-chain construction to a single watcher fanning out new L1 messages. This refactor addressed `tokio::select!` collision issues by classifying updates before handling them. Key decisions included maintaining one `eth_getLogs` call per chain to preserve wire-identical behavior for standalone `kona-node` and ensuring individual fatality for per-chain query channels. The chain set remains fixed at construction, with an empty set resulting in a panic, which is considered correct for the current design.
[#22531](https://github.com/ethereum-optimism/superchain-registry/issues/22531)

### Lokahi Interop Store Design
Initial design decisions for Lokahi's interop stores were made, including the use of RocksDB for persistent storage and a focus on unbounded retention for superroots, with pruning to be considered later. It was clarified that the custom logsdb backend from `op-supernode` is deprecated, and the current reference is `raft-wal`'s fixed-width record layouts. The invalidated-output archive was identified as a critical store whose loss is unrecoverable and fault-proof-visible, necessitating its own database and backup strategy.
[#22535](https://github.com/ethereum-optimism/superchain-registry/issues/22535), [#22540](https://github.com/ethereum-optimism/optimism/issues/22540)

### Engine Reset and Metrics Labeling
Work continued on the `kona-engine`, with discussions around the behavior of `Engine::reset_to` and `Engine::reset`. It was clarified that resets never move the cross-safe head forward, and that the invariant for rewinding the cross-safe head must be maintained explicitly in `kona` due to its storage model. Additionally, the implementation of `chain_id` metric labels was discussed, highlighting challenges with macro surfaces for variadic labels and discrepancies in `cargo test` vs `cargo nextest` behavior for metrics tests.
[#22526](https://github.com/ethereum-optimism/superchain-registry/issues/22526), [#22529](https://github.com/ethereum-optimism/superchain-registry/issues/22529)

## ACTIVE ISSUES

### Kona Engine: Targeted Reset
Discussion on [#22526](https://github.com/ethereum-optimism/superchain-registry/issues/22526) regarding `kona-engine`'s targeted reset functionality confirmed its implementation in #22586. Key points from the implementation notes include:
- Resets never move the cross-safe head *forward*. When rewinding, the cross-safe head must also rewind to prevent invalid forkchoice states.
- `op-node` handles this automatically by recomputing the cross-safe head on every read, while `kona` requires explicit maintenance of this invariant.
- The bound for the cross-safe head belongs in the state transition (`apply_update`) rather than in the reset itself, to maintain the invariant at its source.
- `reset_to` has a bounded number of retries, unlike `reset`, because its target heads are fixed by the caller.

### Kona Engine: Local/Cross-Safe Vocabulary and Promotion
Issue [#22525](https://github.com/ethereum-optimism/superchain-registry/issues/22525) discusses renaming head vocabulary to explicit local-safe/cross-safe and establishing a single cross-safe promotion entry point. The implementation in #22576 highlighted:
- The `cross_safe_head` field is private and written only by `EngineSyncState::apply_cross_safe_promotion`, with `CrossSafePromotion` having a `pub(crate)` constructor, enforcing the "exactly one promoter per engine" property at the crate boundary.
- Two heads required re-pointing: the depth-1 lockstep confirmation to the derivation actor must carry *local*-safe to avoid deadlocks, and `FinalizeTask`'s sanity check moved to *cross*-safe.
- A pre-existing `cargo test` vs `cargo nextest` disagreement on `test_chain_label_metrics` was noted, where `cargo nextest` passes all tests due to running them in separate processes.

### Kona: Chain_ID Metric Label
The discussion on [#22529](https://github.com/ethereum-optimism/superchain-registry/issues/22529) focuses on adding a `chain_id` label to Kona's metrics. The implementation in #22569 revealed:
- The existing macro surface for `set!` and `record!` did not support variadic labels, leading to a new arm where the value is placed first, creating an inconsistent call style.
- The "update the one unit test" instruction was accurate about the count, but the test itself was failing due to `PrometheusBuilder::install_recorder()` setting a process-global recorder, causing panics in `rstest` cases. This was fixed by using `metrics::with_local_recorder`.
- The scope of the PR was limited to `kona-engine`'s 14 call sites, noting that a full sweep across all 8 crates would be a larger effort.
- `chain_id: u64` was added to `EngineState` for easier access to the label, despite duplicating `RollupConfig::l2_chain_id`.
- Several pre-existing lint snags and a disagreement on the failure-counter label schema were noted but not fixed in this PR.

### Lokahi: Interop Actor, Cross-Safe Happy Path (Phase 3)
Issue [#22522](https://github.com/ethereum-optimism/superchain-registry/issues/22522) discusses the Lokahi interop actor's cross-safe happy path. Recent comments index decisions from a Slack design discussion:
- **Retention + storage engine**: Adrian Sutton's decision on [#22535](https://github.com/ethereum-optimism/optimism/issues/22535) indicates RocksDB for stores and an initial default of unbounded retention.
- **WAL-replay hazard for invalidated-output archive**: Discussed on [#22540](https://github.com/ethereum-optimism/optimism/issues/22540), highlighting the need for archive writes to be driven by the interop actor from the WAL, independently of replay branches.
- **Kona/op-supernode activation-source divergence**: A human decision is needed for [#22536](https://github.com/ethereum-optimism/optimism/issues/22536) regarding the difference in interop activation sources between Kona and op-supernode.

### Lokahi: Multi-Chain L1 Watcher
On [#22531](https://github.com/ethereum-optimism/superchain-registry/issues/22531), notes from implementing the multi-chain L1 watcher in #22567 were provided:
- The referenced internal plan file was not found, so the work proceeded based on the issue description.
- `tokio::select!`'s borrowing rules significantly shaped the refactor, requiring updates to be classified before handling to avoid collisions when accessing shared state.
- One `eth_getLogs` call per chain was deliberately maintained to preserve wire-identical behavior for standalone `kona-node`.
- Per-chain query channels remain individually fatal, ensuring current behavior where a closed channel causes the actor to exit.
- Chain labels are intentionally omitted from the watcher's log lines, as #22529 is responsible for chain-labeled telemetry.
- The chain set is fixed at construction and panics if empty, with this invariant confirmed as correct by design in [#22532](https://github.com/ethereum-optimism/optimism/issues/22532).
