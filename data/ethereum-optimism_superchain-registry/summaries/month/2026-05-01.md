# ethereum-optimism/superchain-registry Monthly Report (May 2026)

## 🚀 Highlights
In May 2026, development focused on refining the technical infrastructure of the Superchain, with a particular emphasis on automated maintenance and the hardening of supernode verification logic. Key activities included addressing critical panics in `op-reth` during version upgrades and clarifying the monitoring capabilities of `op-dispute-mon` for diverse game types. The month also saw significant progress in template configurations for upcoming protocol upgrades, specifically regarding the integration of Kona prestates within the Optimism Portal.

## 🛠️ Key Developments

### Infrastructure & Maintenance
The repository maintained a steady cadence of automated updates to ensure consistency across the registry's generated code.
*   **Automated Code Generation:** Multiple updates were performed to synchronize generated code, maintaining the integrity of the registry as the source of truth for Superchain configurations ([#1218](https://github.com/ethereum-optimism/superchain-registry/pull/1218), [#1219](https://github.com/ethereum-optimism/superchain-registry/pull/1219)).

### Protocol & Upgrade Templates
Work began on refining the templates used for smart contract upgrades, ensuring that new fault proof components are correctly referenced.
*   **OPCM Upgrade Templates:** Discussions emerged regarding the `OPCMUpgradeV700` template. A technical correction was identified to ensure `SUPER_PERMISSIONED_CANNON` utilizes `cannonKonaPrestate` rather than the standard `cannonPrestate`. There is ongoing consideration to move this change to the `V800` template to align with smart contract versioning schedules ([#1412](https://github.com/ethereum-optimism/superchain-registry/issues/1412)).

## 🐛 Issues & Triage

### Closed Issues
*   **Monitoring Clarification:** A significant point of confusion regarding `op-dispute-mon` was resolved. It was confirmed that a single instance can monitor both standard CANNON and SUPER_CANNON_KONA games by interfacing with both rollup and supernode RPCs. This confirms that `op-supernode` can effectively expose necessary `op-node` endpoints for monitoring ([#20476](https://github.com/ethereum-optimism/superchain-registry/issues/20476)).

### New & Active Issues
*   **Critical Upgrade Panic:** A fatal panic in `op-reth`'s `StateRootTask` remains a high-priority investigation. The issue occurs during 1.x to 2.x upgrades and appears to be a non-deterministic bug in the parallel trie computation within `alloy-trie-0.9.5`. Standard fixes, such as the legacy state root flag, have proven ineffective ([#20462](https://github.com/ethereum-optimism/superchain-registry/issues/20462)).
*   **Supernode Logic Error:** A logic error was identified in `op-supernode` where `VerifiedRequiredL1` incorrectly calculates the MIN of per-chain L1s instead of the MAX, leading to inaccurate verification data ([#20481](https://github.com/ethereum-optimism/superchain-registry/issues/20481)).
*   **Engine API Refactoring:** Long-standing discussions regarding the duplication of Engine API validations in `Miner.prepareWork` saw renewed interest. Proposed changes include moving specific Optimism-related checks (like L1 attributes deposit data) directly into the Engine API to streamline the codebase ([#688](https://github.com/ethereum-optimism/superchain-registry/issues/688)).

## 💬 Community & Collaboration
The month was characterized by active technical troubleshooting and community engagement on core protocol components. Notable collaboration occurred on issue [#688](https://github.com/ethereum-optimism/superchain-registry/issues/688), where new contributors expressed interest in tackling technical debt related to Engine API validations. Furthermore, the interaction between maintainers and users regarding `op-dispute-mon` configurations demonstrates a healthy feedback loop for clarifying the operational requirements of running Superchain infrastructure.
