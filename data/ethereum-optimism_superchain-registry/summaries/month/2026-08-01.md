# ethereum-optimism/superchain-registry Monthly Report (August 2026)

## 🚀 Highlights
In August 2026, development focused on hardening the Superchain infrastructure through critical version updates for the U20 release candidate and enhanced testing for Programmable Cryptographic Dashboards (PCD). Significant progress was made in refining the `op-deployer` and `OPCM` registry support, alongside targeted efforts to optimize CI performance and resolve synchronization issues between `op-node` and `op-reth`. While the team successfully closed long-standing tasks related to `opgeth-decoupling`, ongoing investigations into event-loop starvation and flaky interop tests remain a priority for protocol stability.

## 🛠️ Key Developments

### Protocol & Network Configuration
The registry saw several updates to ensure compatibility with upcoming releases and network standards:
*   **Sepolia Standard Updates:** Updated `standard-versions-sepolia.toml` to include `op-contracts/v8.0.0-rc.2` for the U20 release candidate [#1298](https://github.com/ethereum-optimism/superchain-registry/pull/1298).
*   **PCD Testing Support:** Added Sepolia versions for `op-contracts/v8.0.0-pcdtest` to facilitate End-to-End (E2E) testing for PCD [#1302](https://github.com/ethereum-optimism/superchain-registry/pull/1302).
*   **Registry Maintenance:** Cleaned up `sepolia-devnet-2` by removing unused contract manager addresses [#1304](https://github.com/ethereum-optimism/superchain-registry/pull/1304) and updated `addresses.json` via automated codegen [#1299](https://github.com/ethereum-optimism/superchain-registry/pull/1299), [#1301](https://github.com/ethereum-optimism/superchain-registry/pull/1301).

### Tooling and Deployment
Improvements were made to the deployment pipeline and core utilities:
*   **OPCM V2 Support:** Fixed `op-deployer 0.7.1` and introduced support for the OPCM V2 Registry [#1303](https://github.com/ethereum-optimism/superchain-registry/pull/1303).
*   **Decoupling Efforts:** Completed the `opgeth-decoupling` initiative, which included the removal of the `check-derivation` tool to streamline the codebase [#21746](https://github.com/ethereum-optimism/superchain-registry/issues/21746), [#22164](https://github.com/ethereum-optimism/superchain-registry/pull/22164).

## 🐛 Issues & Triage

### Closed Issues
*   **CI Optimization:** Resolved concerns regarding CI makespan by shifting toward merging smaller, more manageable PRs rather than large batches [#21186](https://github.com/ethereum-optimism/superchain-registry/issues/21186).
*   **Node Stability:** Addressed an issue where `op-reth` proofs history would lag permanently following a clean shutdown [#22089](https://github.com/ethereum-optimism/superchain-registry/issues/22089).

### New & Active Issues
*   **Synchronization & Performance:** Investigations continue into `op-node` synchronization failures when using the `execution-layer` sync mode with an `op-reth` backend, specifically noting high ECIES error rates [#20974](https://github.com/ethereum-optimism/superchain-registry/issues/20974). Additionally, benchmarking for the Superchain Dependency Manager (SDM) is underway using the `op-benchmark` tool on the SSD devnet [#20176](https://github.com/ethereum-optimism/superchain-registry/issues/20176).
*   **Test Flakiness:** The team is tracking `TestInteropHappyTx` failures, which appear linked to `op-node` driver event-loop starvation [#21940](https://github.com/ethereum-optimism/superchain-registry/issues/21940). Similarly, a SIGSEGV in `reth-optimism-node` integration tests is currently paused while CI is instrumented for better stack trace collection [#20973](https://github.com/ethereum-optimism/superchain-registry/issues/20973).

## 💬 Community & Collaboration
Collaboration this month was characterized by a strong focus on automated maintenance and cross-component debugging. The interaction between the `op-node` and `op-reth` teams was evident in the troubleshooting of synchronization and test failures. The use of automated CircleCI jobs for daily codegen indicates a mature, automation-first approach to registry management, while the resolution of the `opgeth-decoupling` tasks demonstrates successful cross-repository coordination.
