# ethereum-optimism/superchain-registry Weekly Report (Mar 29 - Apr 4, 2026)

## 🚀 Highlights
This week focused on enhancing the robustness of the Superchain ecosystem through critical client updates and a comprehensive audit of error-handling logic across the OP Stack. A significant milestone was reached with the addition of Kona 1.2.12 prestates, ensuring the registry remains synchronized with the latest client versions. Development efforts also prioritized refining interoperability (interop) transaction behaviors during chain reorgs and resolving technical debt within core components like `op-node`, `op-batcher`, and `contracts-bedrock`.

## 🛠️ Key Developments

### Client & Protocol Support
*   **Kona Client Integration:** Successfully integrated prestates for Kona version 1.2.12. This update is essential for maintaining compatibility and ensuring proper state transition validation for chains utilizing the Kona client ([#1206](https://github.com/ethereum-optimism/superchain-registry/pull/1206)).
*   **Protocol Decoding Refinement:** Identified a mislabeling issue in `kona/protocol` where gas-limit decoding errors for span batches were incorrectly reported as `TxNonces`, which could lead to developer confusion during debugging ([#19873](https://github.com/ethereum-optimism/superchain-registry/issues/19873)).

### Core Infrastructure & Bug Fixes
*   **`op-node` & `op-batcher` Stability:** Developers identified several logic errors in node operations, including an incorrect L1 origin comparison in `op-batcher` ([#19859](https://github.com/ethereum-optimism/superchain-registry/issues/19859)) and a channel size calculation bug in `op-node/derive` ([#19858](https://github.com/ethereum-optimism/superchain-registry/issues/19858)). Additionally, a potential resource leak was flagged in the P2P gossip publisher regarding unclosed topics on shutdown ([#19860](https://github.com/ethereum-optimism/superchain-registry/issues/19860)).
*   **Service & Utility Improvements:** Multiple issues were opened to address "leaky" abstractions and incorrect type reporting in `op-service`. Notable fixes include correcting `UnmarshalText` labels for `Bytes256` and EIP-4844 blobs, and addressing a lock leak in `CachingReceiptsProvider` that hindered proper cleanup during fetch errors ([#19862](https://github.com/ethereum-optimism/superchain-registry/issues/19862), [#19875](https://github.com/ethereum-optimism/superchain-registry/issues/19875)).

## 🐛 Issues & Triage

### Closed Issues
*   **Dispute Game Evolution:** The migration of `FaultDisputeGame` chains to `SuperDisputeGame` was closed as the project converges on a unified approach ([#19013](https://github.com/ethereum-optimism/superchain-registry/issues/19013)).
*   **Challenger Progress:** The `op-challenger` issue regarding Kona super executor host arguments was resolved, with the runner now successfully executing `kona-interop` in test environments ([#18287](https://github.com/ethereum-optimism/superchain-registry/issues/18287)).

### New & Active Issues
*   **Contract Clarity:** New issues highlighted contradictions in `contracts-bedrock` error messages. Specifically, the `LivenessModule` and `SystemConfig` contracts contain `require` statements where the revert string contradicts the actual logic (e.g., regarding minimum vs. maximum base fees), which could mislead governance participants ([#19866](https://github.com/ethereum-optimism/superchain-registry/issues/19866), [#19868](https://github.com/ethereum-optimism/superchain-registry/issues/19868)).
*   **Interop Transaction Safety:** A significant discussion is ongoing regarding how the transaction pool should handle interop messages during a reorg. The current consensus leans toward dropping all interop transactions for simplicity and safety, though the team is evaluating whether to re-verify these transactions before re-adding them to the mempool to improve user experience ([#19351](https://github.com/ethereum-optimism/superchain-registry/issues/19351)).

## 💬 Community & Collaboration
The week was characterized by high-level technical coordination between core maintainers. Key contributors like `karlfloersch` and `pcw109550` engaged in deep-dive discussions regarding the safety guarantees of `op-reth` and `op-geth` in the context of interoperability. This collaboration highlights a concerted effort to align different execution client implementations with the Superchain’s safety requirements, particularly concerning how invalid messages are purged from the network during chain reorganizations.
