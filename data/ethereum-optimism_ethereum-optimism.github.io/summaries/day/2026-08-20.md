# ethereum-optimism/ethereum-optimism.github.io Daily Update (Aug 20, 2026)
## OVERVIEW 
Today's development focused on refining the Lokahi interop actor, particularly around multi-chain L1 watching, shared message validity rules, and the initial implementation of interop stores. Significant progress was also made on removing the "cross-unsafe" chain-head notion from the Go codebase.

## KEY TECHNICAL DEVELOPMENTS

### Lokahi Interop Actor Refinements
The Lokahi interop actor saw significant progress with the implementation of a multi-chain L1 watcher, designed to generalize from per-chain construction to handling N chains. This involved adapting to `tokio::select!` constraints and ensuring per-chain system-config filters. The design decision to keep the chain set fixed at construction and non-empty was confirmed. [#22531](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22531)

### Shared Interop Message Validity Rules
Work continued on consolidating interop message validity rules into a single home within `kona-interop`. This involved enumerating existing implementations of activation invariant, timestamp ordering, 7-day expiry, and same-timestamp cycle checks. A key decision was made to structure these rules as methods on a `MessageRules` type for better organization and discoverability. The checksum computation was clarified to belong in Lokahi's store layer rather than shared validity rules. [#22534](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22534)

### Initial Lokahi Interop Stores Implementation
The foundational `lokahi-interop` crate was implemented, incorporating verified, log, and invalidated-output archive stores. Key decisions included using RocksDB for persistence, binary encoding for efficiency, and ensuring the invalidated-output archive's durability due to its critical role in fault proofs. The "O(1) Contains" property for the log store was clarified to be a property of the underlying raft-wal library, not a hard bound for a general KV store. [#22535](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22535)

### Removal of Cross-Unsafe Chain-Head Notion
The "cross-unsafe" chain-head notion, identified as an op-supervisor-era vestige, was removed from the Go codebase across `op-node`, `op-service`, and `op-devstack`. This change specifically targeted the forkchoice label and did not affect the message-level cross-unsafe validation threshold, which remains live functionality in the tx-pool admission path. [#22550](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22550)

## ACTIVE ISSUES

### kona-engine: targeted reset (reset_to with explicit heads) [#22526](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22526)
Discussion centered on the implementation of a targeted reset mechanism, specifically how it interacts with the cross-safe head. It was clarified that resets should never move the cross-safe head forward, and that rewinding the chain requires careful handling to prevent invalid forkchoice states. The `op-node`'s approach of recomputing the cross-safe head on every read was contrasted with `kona`'s stored `cross_safe_head`, highlighting the need for explicit invariant maintenance in `kona`. The discussion also touched upon the retry ceiling for `reset` versus `reset_to`, with `reset_to` having a bounded number of retries due to its fixed input.

### kona-engine: local/cross-safe vocabulary and single cross-safe promotion entry point [#22525](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22525)
The latest comments detail the implementation of renaming head vocabulary to explicit local-safe/cross-safe and enforcing a single promotion entry point for cross-safe. Key points include the structural seal enforced at the crate boundary for `cross_safe_head` and `CrossSafePromotion`, ensuring that promotions cannot be conjured from outside the `kona-engine` crate. The discussion also highlighted the need to re-point certain heads (e.g., depth-1 lockstep confirmation to derivation actor) to local-safe to avoid deadlocks and ensure correct consolidation, while `FinalizeTask`'s sanity check moved to cross-safe. A pre-existing `cargo test` vs `cargo nextest` disagreement on test failures was noted.

### kona: chain_id metric label [#22529](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22529)
The discussion focused on adding a `chain_id` label to Kona's existing metrics. A key challenge was the macro surface for `set!` and `record!` not supporting variadic labels, leading to a design decision where new arms take the value first, resulting in different call styles. The issue also addressed a pre-existing unit test failure related to `PrometheusBuilder::install_recorder()` and its global nature, which was resolved by using `metrics::with_local_recorder`. The scope of the implementation was limited to `kona-engine`'s call sites, with a note that a full sweep across all crates would be a larger effort.

### lokahi: interop actor, cross-safe happy path (phase 3) [#22522](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22522)
The latest comment provides an index of phase-3 decisions from a Slack design discussion. These decisions cover retention and storage engine, a WAL-replay hazard for the invalidated-output archive, and the divergence in activation sources between `kona` and `op-supernode`.

### lokahi: multi-chain L1 watcher [#22531](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22531)
The discussion details the implementation of a multi-chain L1 watcher. A significant challenge was adapting to `tokio::select!` constraints, which required handling all logic after the `select!` expression to avoid borrowing conflicts when dealing with multiple chains. The design deliberately maintains one `eth_getLogs` call per chain per L1 head to preserve the N=1 wire-identical constraint. It was also noted that the chain set is fixed at construction and panics if empty, a design decision confirmed as correct by @ajsutton.

### lokahi: N-chain service composition and config [#22532](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22532)
The latest comment announces the landing of PR #22599, which enables `lokahi node --config <file>` to run N chains in one process. This involved merging parallel branch lines and resolving disagreements regarding L1 head watching, watcher attachment, and the engine's chain ID. A latent test bug exposed by the merge was also addressed. A previous decision from @ajsutton confirmed that the L1 watcher's fixed, non-empty chain set is correct by design, as chains cannot be dynamically added to a running instance.

### kona-interop: consolidate shared message-validity rules [#22534](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22534)
The discussion highlights the consolidation of interop message validity rules. A key decision was made to implement the shared interop rules surface as a `MessageRules` type rather than free functions, following guidance from the Rust code reviewer agent. This improves code organization and discoverability. It was also clarified that checksum computation is not a consensus-protocol check and belongs in Lokahi's store layer rather than in the shared validity rules.

### lokahi-interop: stores (verifiedDB + WAL, logsDBs, invalidated-output archive) [#22535](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22535)
The latest comments announce the landing of PR #22603, implementing the `lokahi-interop` crate with all three stores: verified, log, and invalidated-output archive. Key decisions included using RocksDB for persistence, binary encoding, and placing checksum computation within `lokahi-interop` for now. Two follow-up issues were noted: preallocation in the archive decode path without validation, and reporting unrecognised WAL decision tags as data corruption instead of potential downgrades. Earlier discussions confirmed the use of RocksDB for stores and clarified the "O(1) Contains" property for the logs DB.

### lokahi-interop: verification round loop [#22536](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22536)
The latest comment announces the landing of PR #22605, which implements the verification round loop in `lokahi-interop`. This includes observing chains and L1, making decisions, writing to a WAL, and applying changes. Decisions were made to not write `Invalidate` and `Rewind` to the WAL in this phase, to return a pace instead of sleeping, and to carry through the four verdicts of `local_safe_snapshot_at`. Two issues found during implementation were a potential cold start re-run with a pending WAL slot and a difference in `ExecutingMessage` parser width between Kona and Go. Earlier discussions confirmed that the activation-timestamp override is deferred and clarified the activation source divergence between Kona and op-supernode.
