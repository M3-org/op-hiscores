## ACTIVE ISSUES

- **Kona Engine: Targeted Reset (`reset_to` with explicit heads)** ([#22526](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22526)):
    - Claude confirmed the implementation in #22586. Key insights include that resets never move the cross-safe head forward, and rewinding moves heads backward. The cross-safe head's behavior during rewinds differs between `op-node` (recomputed on read) and `kona` (stored state), requiring explicit invariant maintenance in `kona`. The bound for cross-safe head movement belongs in the state transition (`apply_update`) rather than `reset_to`. `reset_to` has a bounded retry mechanism, unlike `reset`, which retries indefinitely.

- **Kona Engine: Local/Cross-Safe Vocabulary and Single Cross-Safe Promotion Entry Point** ([#22525](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22525)):
    - Claude opened #22576 for this. The discussion highlights that `cross_safe_head` is private and written only via `EngineSyncState::apply_cross_safe_promotion`, with `CrossSafePromotion` having a `pub(crate)` constructor, enforcing the "exactly one promoter per engine" invariant at the crate boundary. Two heads (depth-1 lockstep confirmation and consolidation's `needs_consolidation`) had to be re-pointed to *local*-safe, while `FinalizeTask`'s sanity check moved to *cross*-safe, as finality must not outrun cross-verification. A pre-existing `cargo test` vs `cargo nextest` disagreement on `kona-engine`'s `test_chain_label_metrics` was noted, where `cargo nextest` provides isolated processes, allowing all tests to pass.

    - A decision from Adrian Sutton confirmed that the L1 watcher's fixed, non-empty chain set is correct by design, as chains cannot be dynamically added to a running instance, and a zero-chain configuration is invalid. This means the `select_all` panic on an empty iterator is acceptable, and the invariant should be enforced as a CLI/config error.

- **Kona-Interop: Consolidate Shared Message-Validity Rules** ([#22534](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22534)):
    - Sebastian Stammler noted that the type-3 access-list checksum computation has no Rust counterpart and belongs in the shared rules, with a Go↔Rust golden vector. Claude later clarified, based on Adrian Sutton's input, that the checksum is an implementation detail of the log store for space efficiency, not a consensus-protocol check, and thus belongs in lokahi's logsDB layer ([#22535](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22535)) rather than shared validity rules.
    - A decision was made to make the shared interop rules surface a type, `MessageRules`, with methods rather than free functions, following `rust-code-reviewer` agent guidance for better organization and discoverability.
    - Claude provided a detailed enumeration of every pre-existing implementation of the five rules (activation invariant, timestamp ordering, 7-day expiry, checksum existence, same-timestamp cycle check) across Rust and Go. It was noted that Rust had no implementation for checksum existence, and adding one would be a semantic addition. Three Rust↔Go divergences were identified: activation source (kona per-chain vs op-supernode cluster-wide), expiry arithmetic, and initiating-message existence (checksum + logsDB vs receipt refetch).

- **Lokahi-Interop: Stores (verifiedDB + WAL, logsDBs, invalidated-output archive)** ([#22535](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22535)):
    - Adrian Sutton decided that superroots must be returnable over the full fault dispute window, with an option for unbounded retention (likely default), meaning no pruning initially. This implies using RocksDB for stores and keeping the logs DB behind a trait.
    - A correction to the brief noted that `op-supernode` moved to a raft-wal implementation for logsdb, and the custom logsdb backend is not desired. The "O(1) `Contains`" property was analyzed, distinguishing between log index to log hash (fixed stride) and block number to record bytes (raft-wal's dense integer-indexed offset table). Sizing estimates showed logsDB dominating storage. The invalidated-output archive was highlighted as the only store whose loss is unrecoverable and fault-proof-visible, requiring its own database and backup story.

- **Lokahi-Interop: Verification Round Loop** ([#22536](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/22536)):
    - Adrian Sutton decided to defer the activation-timestamp override for now, keeping it as a potential follow-up. This means interop activation for the initial release will be the Lagoon timestamp, and per-chain depset activation is deferred.
    - Claude clarified that the cluster-wide vs per-chain activation divergence between `op-supernode` and `kona` is not a live risk today because `op-supernode` requires all chains' `LagoonTime` to be identical at startup. Therefore, `kona`'s per-chain fork check can be ported as-is.
