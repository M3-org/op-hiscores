## ACTIVE ISSUES

### Flaky Test: `TestExecutePayloadSuccess` ([#19898](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/19898))
- The issue was reopened due to a recurrence of the proofs ExEx store readiness race in `TestL2MultipleTransactionsInSingleBlock`. The problem stems from the test waiting for the store only through `receipt1.BlockNumber`, while `receipt0` can land in a later block, causing a race condition when fetching proofs. A fix in #21807 addresses this by waiting through the later of both receipt blocks. Previous attempts to fix involved `WaitForBlockNumber`, which was insufficient as it only checked the validator's EL head, not the asynchronously populated proofs ExEx store.

### op-reth-test-engine: minimal in-test EL for op-e2e/actions ([#20415](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/20415))
- The engine is now complete, and the full track (this issue + #21196) is implemented as a draft stack. FCU-with-attrs is now supported, and processed payloads remain non-canonical until an FCU makes them head, aligning with Engine API semantics. The generic subprocess-IPC client plumbing has been moved to a shared `op-service/engineipc` package for reuse.

### op-proposer: select proposal sources by root format instead of interop mode ([#21710](https://github.com/ethereum-optimism/ethereum-optimism.github.io/issues/21710))
- Discussion revolves around how to best address the op-proposer classifying proposal sources using stale interop mode lists. One proposed solution is to rename CLI options like `--supernode-rpc` to `--superroot-rpc` to make the user explicit about what they are fetching, rather than implementing a more complex system that could lead to confusion.
